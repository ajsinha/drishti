Data inbox: option C, table-first (one table of files, one of cycles)alternative

The Inbox tab as a compact admin page in the style of the Loads tab: a row of counts (waiting, loading, loaded today, failed, next cycle), then one table of every file of the day wherever it is (inbox/, inprocess/, outbox/, failed/) with its state, route, dates, rows, rejects, run and Retry, filtered by place; then the cycles, the routing rules and the settings. Each mock-up shows two scenes: a quiet afternoon (one small run done, three files waiting) and a busy one (a 23-minute run of a 6.2 GB scenario archive, two cycles skipped because runs never overlap, Load now answered skipped, ready.all waiting for the next cycle, and one failed file with Retry). Times are the server's, UTC; a run id is its start time and node.

How it feels

  • Densest: one line per file, sortable and filterable; the question "where is my file?" is one search.
  • Looks like the Loads tab beside it: nothing new to learn.
  • Failed and loading rows float to the top, tinted.

Trade-offs

  • The flow (waiting → loading → done) is a column, not a picture: a newcomer learns less.
  • Wide: on a phone the table scrolls sideways inside its frame.
  • A long run's progress is spread over rows.

Build

  • Cheapest: the console's existing table component (sort, filter, page) and pills.
  • The files table joins the status's waiting files, the run's folder and the ledger by name.
  • Works without scripts as a plain page.
Mock-up. Design, not built: Admin → Data loads → Inbox (planned, DATALOAD_INBOX.md section 10). Every number is invented for the picture. The data comes from GET /api/v1/admin/dataload; Load now is POST …/run, Retry POST …/retry (both loads:write). On a node that is not the owner the tab names the owner and links to it. Phone width: columns stack, tables scroll in their frame, controls are touch sized. Open with #light for the light theme.
