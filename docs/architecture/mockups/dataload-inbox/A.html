Data inbox: option A, a status board (waiting · loading · done)recommended

Admin → Data loads gets an Inbox tab. Option A draws the inbox as three columns that follow a file's way through the folders: Waiting (inbox/, each file with its state: ready, not yet stable, no marker, or ready via ready.all, and the rule that will route it), Loading (inprocess/<run>/, table by table) and Last cycles (outbox/: files, tables, dates, rows, rejects, time, outcome, skipped cycles). Failures with Retry, duplicates, the routing rules and the settings sit below; the engine's switch, owner node, lock, next cycle and Load now sit on top. Each mock-up shows two scenes: a quiet afternoon (one small run done, three files waiting) and a busy one (a 23-minute run of a 6.2 GB scenario archive, two cycles skipped because runs never overlap, Load now answered skipped, ready.all waiting for the next cycle, and one failed file with Retry). Times are the server's, UTC; a run id is its start time and node.

How it feels

  • The columns are the folders: an administrator learns the hand-shake by looking.
  • One glance answers the three questions: is anything stuck, what is next, did it load.
  • The routing preview warns before a file fails (no rule matches).

Trade-offs

  • History is short (the last cycles); the full list is the ledger link and the Loads tab.
  • Three columns need width: below 1000 px they stack (phone: rows that open).
  • Skipped cycles take room in a busy hour (two rows here).

Build

  • GET /api/v1/admin/dataload already gives the switch, owner, lock, next cycle, the run's start, waiting files with their state, failures, cycles and the ledger; it gains the run's files and tables, each waiting file's rule and the rules in effect.
  • Polls every 5 s while a run loads, 30 s when quiet.
  • Reuses the Loads tab's tables, pills and the engines switch.
