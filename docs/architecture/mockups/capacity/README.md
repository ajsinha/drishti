# Admin → Capacity (proposed): a single-node capacity planner

The product owner asked: *"Maybe we can add a page for this capacity planner in admin menu?"* and then *"Like var playground I
should be able to export live formula driven excel sheet from ui."* These are the mock-ups to choose from.

**Status: built** as chosen (B as the landing view, A behind *Edit the plan*; C not built). The page is documented in
[OPERATIONS.md 12.4](../../../admin/OPERATIONS.md#124-admin--capacity-today-against-the-plan); the build checklist is in section 7.

The page is the planner workbook
([`docs/architecture/Drishti-Sizing-Planner.xlsx`](../../Drishti-Sizing-Planner.xlsx), generated by `tools/sizing_planner.py`;
[RESOURCES_AND_SCALE.md 9.7](../../RESOURCES_AND_SCALE.md#97-sizing-a-single-node-the-planner-workbook)) as a screen. It shows the same
inputs and the same results: the heap of a date term by term, the dates in memory, the intraday layer, the caches, the users and the loads;
the recommended `-Xmx` and collector; RAM (heap, native, page cache); disk by folder with the free-space guard; cores; the settings with
their exact keys; every JVM argument with its condition and the whole command line; and the warnings in words.

Every mock-up uses the product owner's production shape: 300,000 trades (positions = trades), 39% of them updated intraday (117,000 a day,
10 batches assumed), 10 dates in memory, 50 users, Java 21. The figures are **illustrative**: the planner's formulas at those inputs, with
the coefficients calibrated to the 1,000,000-position re-benchmark (-Xmx10g, G1, 24 GB RAM, 450 GB disk, 8 cores; the automatic safety net
too small, so `drishti.var.open-heap-mb: 3584`).

Open each file in a browser; dark theme by default, `#light` for light. The PNGs are the light theme.

| Option | File | One line |
|---|---|---|
| A, Planner | [A.html](A.html) · [A.png](A.png) | The whole workbook as one live page: grouped inputs on the left, every result on the right recomputing as you type. For the engineer who sizes a server. |
| B, Today against the plan | [B.html](B.html) · [B.png](B.png) | The running server's measured figures beside the plan, a green/amber/red headroom bar per resource, "what breaks first" in words with the fix, and growth sliders (×1.5, ×2, ×3 trades). For the operator who asks "are we fine, and for how long?" |
| C, Wizard | [C.html](C.html) · [C.png](C.png) | Four questions (data → dates in memory and pins → users → machine), three plain choices each, ending on a summary card with the settings and the command line. For the first-time planner; links to A. |

Common to all three: a "Why?" on every result line (the formula in words and where the coefficient comes from); a prominent
**Download the working (.xlsx)** action with its dialog; the Admin tab placed after Caches; a phone tier.

**Recommendation.** B as the page's landing view with A behind "Edit the plan" (one page, two modes: B answers the daily question, A
the sizing one); C later, only if first-time users struggle with A.

## 1. Placement

A new Admin tab **Capacity** (`/admin/capacity`), after **Caches** in `drishti-console/web/templates/admin/_nav.html`, shown by the
edition's `admin.pages` like every other Admin page (`admin_page_shown('capacity')`); administrators only. The command line word
`ADMIN CAPACITY` opens it.

**Release (proposed, pending the product owner):** 2.9.13, the "Java 25 and performance I" release: the planner is calibrated by that
release's benchmarks, and Java 25 changes its heap factor and JVM arguments.

## 2. One coefficients file

Today the coefficients live as a Python list in `tools/sizing_planner.py`. The proposal moves them, with the inputs' defaults and the
results' formulas, into one data file, read by all three consumers:

```
drishti-server/src/main/resources/capacity/planner.yaml
  inputs:        name, group, label, default, unit, kind, hint            (the INPUTS list today)
  coefficients:  name, value, unit, status (measured|formula|calibrated|estimate), source   (COEFFS)
  results:       name, band, label, formula, unit, why                   (the Results formulas, Excel syntax)
  jvm:           name, flag, formula, condition, why, source             (JVM)
  warnings:      name, label, formula                                    (WARNINGS)
```

- `tools/sizing_planner.py` reads it to write the committed workbook and the template (below); `--check` still fails when they drift.
- The server evaluates the same formulas for the page (a small evaluator of the subset used: names, `+ - * / ^ &`, comparisons, `MAX`,
  `MIN`, `IF`, `CEILING`, `AND`, `OR`, `INT`, `ROUND`, the same subset the Python evaluator implements), so the page and Excel cannot
  disagree. A shared test vector (the `EXPECTED` and `EXPECTED_BENCH` figures) runs against both evaluators.
- A measurement of your own server changes one coefficient in one file, and the page, the workbook and the tool follow (overrides
  of single coefficients from the server's configuration are planned).

## 3. Download the working (.xlsx): the VaR Playground's way

As the VaR Playground exports a live, formula-driven workbook, the Capacity page exports the planner workbook with every result a live
Excel formula over the **Inputs** and **Coefficients** sheets.

- **The template.** The generator's output, with named input cells, is shipped in the server's resources, as the Playground's is:
  `drishti-server/src/main/resources/capacity/template/` (the parts of the xlsx: Results, Coefficients, Explain, Calibration check, the
  styles from `playground/var/template/xl/styles.xml`), written by `tools/sizing_planner.py --template`.
- **The fill.** The server writes only the Inputs sheet (and, when asked, a **Live** column of the server's measured figures, with the
  time they were measured) and streams the zip with `SheetStream` (`server/playground/SheetStream.java`, as `VarPlaygroundBook` does).
  Results and Coefficients are copied from the template untouched, so every formula stays live: change an input in Excel and the heap, RAM,
  disk and cores recompute.
- **The dialog** asks which inputs: *what is on the screen*, *this server's live figures*, or *both, as two Inputs columns* (Plan and
  Live; Results computes each, so the gap is reproduced in formulas). It states that this is the same formula workbook as
  `docs/architecture/Drishti-Sizing-Planner.xlsx`.
- **Endpoint:** `GET /api/v1/admin/capacity.xlsx?inputs=plan|live|both&Trades=300000&HotDates=10&Users=50&JavaVersion=21&…` (any input
  by its workbook name; unknown names refused with the list of valid ones). Also `GET /api/v1/admin/capacity` (the plan's results as
  JSON for the page) and `GET /api/v1/admin/capacity/live` (the measured figures below).
- **CLI:** `drishti.py admin capacity` (the results as a table), `drishti.py admin capacity --xlsx FILE [--inputs plan|live|both]
  [--set Trades=300000 …]`.
- **Admin-only and audited:** `entitlements.requireAdmin`; each download recorded as `capacity-workbook-downloaded` with the inputs
  chosen. Saving a plan (A, "Save plan") is audited as `capacity-plan-saved`.

## 4. The live figures for option B

Each from an endpoint the server already has, except two small additions:

| Figure | Source |
|---|---|
| Positions of the newest date, dates loaded | `GET /api/v1/var/status` → `loaded` |
| Dates open, hot-dates, open dates' heap and the safety net, protected dates | `GET /api/v1/var/status` → `memory.openDates`, `hotDates`, `memory.openHeapBytes`, `memory.openHeapLimitBytes`, `memory.protected` |
| Mapped hot-file bytes, machine RAM, page-cache room | `GET /api/v1/var/status` → `memory.mappedBytes`, `memory.physicalMemoryBytes`, `memory.pageCacheRoomBytes` |
| Heap used and max (-Xmx), cores, Java version | `GET /api/v1/admin/health` → `server.heapUsedMb`, `server.heapMaxMb`, `server.cpus`, `server.java` |
| Disk free and the guard, size per folder | `GET /api/v1/admin/caches` → `disk.freeBytes`, `disk.guardBytes`, `disk.folders`; also `GET /api/v1/admin/health` → `disk` |
| Cache budget and use | `GET /api/v1/admin/caches` → `memory.budgetBytes`, `memory.usedBytes` |
| Heap after GC | `/actuator/metrics/jvm.gc.live.data.size` (Micrometer; already used by the platform alert rules) |
| Requests a second, peak today | `/actuator/metrics/http.server.requests` (count, rated over a minute; the server keeps today's peak); in a cluster also the Net digest's `load.requestsPerSecond` |
| **Resident memory (RSS)** | *to add*: `server.rssMb` in `/api/v1/admin/health`, from `/proc/self/status` (VmRSS) on Linux, absent elsewhere |
| **Users now and at today's peak** | *to add*: the console's signed-in sessions active in the last 5 minutes, reported by the console |

"What breaks first" is computed, not written by hand: each resource's live use plus what the plan says is still to come today (the
intraday layer grows with the batches; dates open up to hot-dates), against what the server has (`-Xmx`, RAM, disk free minus the guard,
cores × the measured rate). The first one short or nearest, with its symptom and the setting that fixes it, is said in a sentence.

## 5. Phone tier (MOBILE_DISPLAY: must / glance / more / desk)

| Tier | A Planner | B Today against the plan | C Wizard |
|---|---|---|---|
| Must | the four answers (heap, RAM, disk, cores), the warnings | what breaks first in one sentence, with the fix; the four states | the four answers, the warning |
| Glance | the heap bar by part | one line per resource, live / limit and its state | the steps work on a phone (one question a screen) |
| More | the settings with their keys, collapsed | the live-against-plan table and growth, collapsed | what the heap holds, disk |
| Desk | inputs, JVM arguments, the command line, the download | the growth sliders, the download | the command line, the download |

## 6. Not in scope

A cluster planner (sharded members divide hot files, page cache and loads but each copies the skeleton): the workbook's cluster sheet
comes first, then a "Cluster" mode of this page. No figure on the page is a measurement unless it is in the Live column, with its time.
