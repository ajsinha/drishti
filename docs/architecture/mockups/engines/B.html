How it feels

  • Friendly and visual: a card per engine, grouped as the business thinks (market, counterparty, platform).
  • The dependency map makes 'what needs what' obvious at a glance.
  • One dialog per change, with the reason and the consequence.

Why not recommended

  • Cards spend the screen: ten engines fill it, and more engines will come.
  • Where a switch is set (file, local file, environment) and threads do not fit on a card.
  • A dialog per change; no batch of several changes with one reason.

Worth keeping

  • The dependency map, as a small drawing in A's side panel.
  • Grouping by family, as a filter in A's table.
  • The 'off hides' line on each card, as A's hover text.
Mock-up. Design, not built (docs/guides/ADMIN_GUIDE.md). Names, numbers, nodes and the reference codes (DRS-1020 to DRS-1024) are illustrative; the codes are assigned when it is built. A change writes the engine's file config/engines/<id>.yaml, is audited with who, when and why, and is the same from drishti.py server engines.
