How it feels

  • The page Functions already uses: a list, a staged change, a review panel with the reason, then History.
  • Before Apply, the two facts that matter: what depends on it and what disappears for people.
  • Memory and threads per engine answer 'what does this server spend on what'.

Why recommended

  • Nothing new to learn: the same flow as turning a command off.
  • Fits the single server most installs are; the cluster is one tab away (option C's matrix).
  • Says where each switch comes from (file, local file, environment), so a change never silently fails.

Trade-offs

  • Dependencies are read from columns, not drawn (B draws them).
  • Several nodes at once only in the Cluster tab.
  • A long row of columns: on a phone the table scrolls sideways; the side panel stacks below.
Mock-up. Design, not built (docs/architecture/COMPUTE_ENGINES.md). Names, numbers, nodes and the reference codes (DRS-1020 to DRS-1024) are illustrative; the codes are assigned when it is built. A change writes the engine's file config/engines/<id>.yaml, is audited with who, when and why, and is the same from drishti.py server engines.
