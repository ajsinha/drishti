Overload defences: option A, calm messages in place with a countdown and automatic retryrecommended

When the server is short of room, the thing you asked for says so where you asked for it: what is busy, a countdown to the next try, and it tries again by itself (Try now and Cancel beside it). Nothing else on the screen changes. The countdown is the server's own Retry-After, so the server keeps no list of waiting requests.

"Let everything through" turns the waits off (the server can then run out of memory); "Hold all new heavy work" is for a planned restart: signed-in people keep reading. Either ends by itself and goes back to Automatic.

How it feels

  • The message sits exactly where the click was; the rest of the page is untouched.
  • A countdown ring and plain words: what is busy, when it tries again.
  • Automatic retry by default (up to three times), Try now and Cancel always there.

Why recommended

  • Matches the 503 + Retry-After contract one to one: the server stays stateless while short of memory, which is when it must not take on more.
  • Same behaviour in the console, the API and drishti.py --wait; works the same on every member of a cluster.
  • Smallest build (one message component, one retry helper); no new screens to learn.

Trade-offs

  • No overall view of what you are waiting for if you start several things (B's tray).
  • Many people retrying at once: spread by a small random jitter added to the Retry-After.
  • A closed tab forgets the retry (the request was never started, so nothing is lost).
Mock-up. Design, not built. Names, numbers and the reference codes (DRS-95xx) are illustrative; the codes are assigned when it is built. Every refusal is HTTP 503 with Retry-After and a DRS- code; drishti.py and the API print the same words.
