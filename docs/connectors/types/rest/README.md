# The rest connector

Built-in connector `rest` (`plugins/drishti-connectors`, package `plugin.rest`): reads an entity from a service that already has a per-entity JSON API, copying
nothing. Every view is one request to the service.

## What it reads

For a read of `<kind>/<id>` it sends `GET <base-url><path>` with `{kind}` and `{id}` replaced by the URL-encoded kind and id
(`URLEncoder`, `+` turned into `%20`, so `/` becomes `%2F`), with `Accept: application/json` and every `header.<Name>` setting. One
JDK `HttpClient` per connector, connections kept alive; `timeout-ms` is both the connect and the request timeout; redirects are not
followed. Its manifest is `SourceCapabilities.FETCH_ONLY`: no search, no type-ahead, no reverse lookups, no live updates, not dated.
Every other question about its kinds must be answered by another connector.

### When to use it

| Use it for | Prefer another store for |
|---|---|
| an owning system that already has a per-entity JSON API, and you want its current answer, not a copy | history: a picked business date (Delta Lake, a JDBC table, files) |
| reference or account data opened one entity at a time (a counterparty, a client, a limit) | kinds users search for, type ahead on, or filter (`TRD where …`): the connector cannot search |
| a first integration before a feed or a database load exists | links back to an entity (*Linked entities*, impact with F8): it has no reverse lookups |
| data whose owner does not allow copies | anything that must tick live: it has no subscriptions |
| a small number of views a minute | a million entities a day listed, aggregated or scanned: it reads one entity per request |

### How a read becomes a request

| Step | Exactly what the code does |
|---|---|
| base URL | `base-url` with every trailing `/` removed (`https://crm.bank.example/api/` becomes `https://crm.bank.example/api`) |
| path | `path` (default `/{kind}/{id}`), with each `{kind}` and `{id}` replaced; the rest is used as written, so it may hold a fixed query string |
| encoding | `URLEncoder.encode(value, UTF-8)` with `+` turned into `%20`: a space becomes `%20`, `/` `%2F`, `+` `%2B`, `:` `%3A`, `&` `%26` |
| method and headers | `GET`, `Accept: application/json`, then every `header.<Name>` setting as a request header `<Name>` |
| client | one JDK `HttpClient` per connector, built at start and shared by every concurrent read (virtual threads); connections kept alive |

With `base-url: https://crm.bank.example/api`:

| `path` | Entity | Request |
|---|---|---|
| `/{kind}/{id}` (default) | `counterparty/CP-HARBOURVIEW` | `GET …/api/counterparty/CP-HARBOURVIEW` |
| `/{kind}/{id}` | `trade/T 1` | `GET …/api/trade/T%201` |
| `/v2/{kind}s/{id}` | `position/POS-77` | `GET …/api/v2/positions/POS-77` |
| `/{kind}/{id}.json` | `counterparty/CP-HARBOURVIEW` | `GET …/api/counterparty/CP-HARBOURVIEW.json` (a static file server) |
| `/lookup?type={kind}&key={id}` | `book/BOOK RATES/3` | `GET …/api/lookup?type=book&key=BOOK%20RATES%2F3` |

Many servers and proxies reject or decode `%2F` in a path; a service whose ids contain slashes takes them in the query string.
Because ids are encoded, an id cannot change the path or add query parameters.

The site-wide settings summary is in [CONFIGURATION.md](../../../admin/CONFIGURATION.md#rest-tls-proxy). Server settings that
bear on it: `drishti.sources.fetch-timeout` (10 s, the whole read across every connector tried), `drishti.sources.routes.<kind>`
and `drishti.graph.link-budget` (40 ms). A header name is written as it is (`header.X_Client`); no bracketing is needed.

**Which kinds a connector serves.** The connector's own `kinds:` list wins; without it `settings.kinds`; with neither, **every
kind**: the connector is then asked whenever the connectors before it miss an entity of any kind, and a `400`/`500` for a kind
the service does not know fails that read with `DRS-1003` instead of reaching the next connector. Always give a REST connector
its kinds.

## Data structure

The service's answer decides everything:

| Answer | Becomes |
|---|---|
| `404` | not held here: the next connector for the kind is asked |
| any other status of 400 or more | a failure (`<source-name> answered HTTP <status> for <kind>/<id>`, `DRS-1003`); not passed on |
| below 400 (`200`, `204`, `3xx`) | the body parsed as JSON is the document; an empty body is an empty document, *found* |

- **Document:** the body exactly (any JSON value; services return an object), nested structures as the service sends them.
- **Id rule:** the entity id is what the user asked for; the service maps it. `path` may move it into the query string
  (`/lookup?type={kind}&key={id}`) for ids holding `/`.
- **Generation:** the response header `generation-header` (default `ETag`) with every `"` removed, if only digits remain (`ETag: "77"` →
  77; a weak `W/"77"` is not); otherwise the fetch time in milliseconds.
- **Provenance:** `live: false`, `businessDate: null`: the document is the service's current answer.

Two consequences of the status rules: **redirects are not followed** (the JDK client has no redirect policy, so a `301`/`302`
body, often HTML or empty, is parsed as the document: point `base-url` at the final address, for example `https://`, not one
that redirects); and **an empty body is not "not held"** (a service that has nothing for an id must answer `404`). A connection
refused, a TLS or DNS failure, a timeout, or a body that is not JSON is a `DRS-1003` failure too. The body is streamed into the
document tree without an intermediate copy.

| Response header | Generation |
|---|---|
| `ETag: "77"` | `77` |
| `X-Version: 42` with `generation-header: X-Version` | `42` |
| `ETag: W/"77"` (a weak ETag) | not digits: the fetch time in milliseconds |
| `ETag: "a1b2c3"`, or no such header | the fetch time in milliseconds |

Without a numeric version header two reads of an unchanged entity carry different generations.

What Drishti records (`GET /api/v1/entities/counterparty/CP-HARBOURVIEW/raw`, connector `crm-api`):

```json
{"ref": {"kind": "counterparty", "id": "CP-HARBOURVIEW"},
 "provenance": {"source": "crm-api", "generation": 42, "fetchedAt": "2026-10-01T09:14:03.118Z", "live": false,
                "businessDate": null},
 "data": {"COUNTERPARTY_ID": "CP-HARBOURVIEW", "NAME": "Harbourview Capital LLP", "…": "…"}}
```

```http
GET /api/counterparty/CP-HARBOURVIEW HTTP/1.1
Accept: application/json
Authorization: Bearer eyJ…

HTTP/1.1 200 OK
X-Version: 42

{"COUNTERPARTY_ID": "CP-HARBOURVIEW", "NAME": "Harbourview Capital LLP", "RATING": "A", "NETTING_SETS": ["NS-HARBOURVIEW-ISDA"], …}
```

## Examples

```yaml
# config/connectors/pricing-api.yaml
plugin: rest
kinds: [price]
description: Prices from the pricing service
settings:
  base-url: https://pricing.example.com/api
  path: /{kind}/{id}
  timeout-ms: '1500'
  generation-header: X-Version
  header.Authorization: Bearer ${PRICING_TOKEN}
# the pack (or application.yaml) routes the kind:  routes: { price: pricing-api }
```

Ready-made files in `config/connectors.examples/other/`: `pricing-api.yaml` (TLS with a PKCS12 truststore), `rest-mtls.yaml` (private CA
and a client certificate) and `rest-via-proxy.yaml` (a vendor API through the corporate proxy). There is no loader. A connector file is applied to the
running server within seconds, edited in any editor, in **Admin → Connectors** (a form, a YAML tab, **Test connection**) or with
`drishti.py connector apply` ([../../../guides/DATA_GUIDE.md section 9](../../../guides/DATA_GUIDE.md#9-connector-files-and-admin--connectors)).

A pack suggests the same as a template in `config/packs/<domain>/<pack>/pack.yaml` (keys with dots written flat); the server writes
it to `config/connectors/crm-api.yaml` at the first start if the site has none, and the file is then the site's:

```yaml
connectors:
  crm-api:
    plugin: rest
    kinds: [counterparty]
    settings:
      base-url: ${CRM_URL:http://localhost:9000/api}
      path: /{kind}/{id}
      timeout-ms: 2500
      generation-header: X-Version
      header.Authorization: Bearer ${CRM_TOKEN:}
routes:
  counterparty: crm-api
```

The shipped `application.yaml` also lists the plugin as itself, off (`drishti.sources.plugins.rest`, `DRISHTI_REST_ENABLED=false`,
`DRISHTI_REST_URL=http://localhost:9000/api`): enabled, it runs under the name `rest` and serves every kind unless
`settings.kinds` is set. Prefer named connectors: each has its own name in health, routes and provenance.

### Try it

Any static file server stands in for the API (`base-url: http://localhost:9000/api`, `path: /{kind}/{id}.json`):

```bash
mkdir -p /tmp/crm/api/counterparty
echo '{"COUNTERPARTY_ID": "CP-HARBOURVIEW", "NAME": "Harbourview Capital LLP", "RATING": "A", "COUNTRY": "GB"}' \
  > /tmp/crm/api/counterparty/CP-HARBOURVIEW.json
(cd /tmp/crm && python3 -m http.server 9000)
curl -s http://localhost:18480/api/v1/entities/counterparty/CP-HARBOURVIEW/raw | jq -c '{provenance, data}'
```

You should see `"source":"crm-api"`, `"live":false`, `"businessDate":null` and the document; `CPTY CP-HARBOURVIEW <GO>` opens it.

## Read paths and what each costs

| Read path | Supported | Cost on the service |
|---|---|---|
| open one entity (`CPTY CP-HARBOURVIEW <GO>`, `GET /api/v1/views/{kind}/{id}`) | yes | one `GET` per open, every time; nothing is cached |
| the entity's document (`/raw`) | yes | one `GET` |
| linked entities shown in a view | yes, each through the router | one `GET` per linked entity of a REST-served kind, in parallel, within `drishti.graph.link-budget` before the link shows as *pending* |
| type-ahead, structured search (`CPTY where rating = 'A'`), pick lists | no | none; users type the whole id, or another connector lists the kind's ids |
| a picked business date | no (undated) | tried after every dated connector; when it answers, the view says *No data held for 2026-09-29: the current data of crm-api, a source that keeps no dates* |
| reverse lookups (*Linked entities*, impact F8) | no | none; other connectors may still answer what refers to the entity |
| live push | no | none; views do not tick unless a live connector pushes the kind |
| derived kinds over a REST kind | members are listed by search | the members' documents are read only if another connector lists their ids |

Reads for the same entity are not merged: ten users opening the same counterparty send ten requests.

## Dates, and pairing with a dated store

The router builds a kind's candidates from its route, then the default route (`demo`), then every other connector that serves
it. For a **picked date** dated connectors go first, so the service is asked only when no dated store holds the entity. For
**Live**, live connectors go first and then the route decides whether the service or a dated store answers. A common
arrangement: the service is the truth for *now*, a nightly copy in a lake is the history (`crm-api` above, plus the core pack's
Delta Lake connector `reference-store`, with `routes: { counterparty: crm-api }`):

| The user asks for | Order tried | Who answers |
|---|---|---|
| Live | `demo` (live) → `crm-api` (the route) → `reference-store` | the samples if they hold the id, else the service; a `404` falls through to the lake's newest date |
| a picked date | `reference-store` (dated) → `crm-api` → `demo` | the lake, for that date |
| a date the lake does not hold | as above | the service's current answer, with the *No data held for <date>* banner |

With `routes: { counterparty: reference-store }` instead, Live reads come from the lake's newest date and the service is asked
only for counterparties the lake does not hold. Switch the samples off (`DRISHTI_DEMO_ENABLED=false`) when the service holds the
same ids as the samples.

## Scale, limits and timeouts

- **Throughput is the service's.** Every view open, and every linked entity of the kind, is a request; the service's answer time
  is added to the view. Size the service for the views users open, not for the size of the book.
- **No bulk path:** no listing, batch request or column read. For search, type-ahead, aggregation or impact load the same data
  into a dated store ([Delta](../../../../plugins/drishti-plugin-delta/README.md), [JDBC](../../../../plugins/drishti-plugin-jdbc/README.md),
  [files](../file/README.md)) and keep the service for the current answer.
- **No cache, no memory:** nothing grows with the number of entities, nothing is kept on disk.
- **Concurrency:** reads share one HTTP client with no limit on requests in flight; rate limits belong in a gateway in front of
  the service. A `429` is a failed read, not a retry. **No retries:** opening the view again sends a new request.
- **One URL pattern per connector:** services with different paths per kind need one connector each.

Two timeouts apply, and the shorter wins: `timeout-ms` (2000; connection set-up and the response; past it `DRS-1003`) and
`drishti.sources.fetch-timeout` (10 s; the **whole** read across every connector tried; past it `DRS-1004 timed out reading
<kind>/<id>`). Keep `timeout-ms` below `fetch-timeout` with room for the connectors tried first, so the user sees which connector
failed. To allow a service 15 s, set `timeout-ms: 15000`, `drishti.sources.fetch-timeout: 20s`, and the console's
`backend.timeout_seconds` above it (`25`). When `fetch-timeout` ends a read first, the HTTP request is not cancelled; it finishes
or reaches `timeout-ms` in the background.

## Failure and recovery

Nothing long-lived but the HTTP client, so nothing to reconnect. Health is `UP` once started (`DOWN: not started` before). A
service that is down **does not change health**: it shows as failed reads, `DRS-1003 crm-api failed reading
counterparty/CP-HARBOURVIEW`, counted under the connector's `reads` in `GET /api/v1/admin/health`:

```json
{"name": "crm-api", "status": "UP", "health": "UP", "kinds": ["counterparty"], "live": false, "dated": false, "search": false,
 "reads": {"reads": 12, "found": 7, "notHeld": 1, "errors": 4,
           "lastError": "IOException: crm-api answered HTTP 503 for counterparty/CP-HARBOURVIEW", "…": "…"}}
```

Alert on `reads.errors`, `lastError` and `lastErrorAt`. When the service comes back the next read works. At start an empty
`base-url` (`rest plugin needs settings.base-url`) or a `timeout-ms` that is not a whole number lists the connector under
`failedToStart`; the server runs on without it. The service is not contacted at start.

## Security

- **Credentials** go in request headers (`header.Authorization: "Bearer ${CRM_TOKEN}"`, `header.X-Api-Key: "${CRM_KEY}"`), the
  value in the environment, never in a file. A placeholder whose variable is unset is sent as written and answered `401`; use
  `${CRM_TOKEN:}` only where empty is acceptable. Headers are fixed at start: a token that expires needs a restart (or a
  long-lived service token); there is no OAuth client flow.
- **Settings are not shown** by health or `/api/v1/sources`.
- **What leaves the server:** the kind and id of every entity a user opens (and every linked entity of the kind), with the
  connector's credentials, not the user's. Entitlements and redaction are applied by the Drishti server to what it shows.

### TLS for the REST connector

An `https://` base URL is checked against the JVM's authorities and the host name unless the connector's own `tls.*` settings
say otherwise ([DATA_GUIDE.md section 10](../../../guides/DATA_GUIDE.md#10-tls-and-the-outbound-proxy); keys in [CONFIGURATION.md](../../../admin/CONFIGURATION.md#shared-tls)):
`tls.ca-file` or `tls.truststore` for a private CA (`tls.trust-jvm-default: true` keeps the public ones too), `tls.cert-file` +
`tls.key-file` (or `tls.keystore`) for mutual TLS, `tls.verify-hostname: false` to check the chain but not the name. Each
connector has its own, so two services can use two CAs. `tls.*` with an `http://` URL is a start-up error, never a silent
downgrade; the `-Djavax.net.ssl.*` JVM properties apply when the connector has none of its own.

```yaml
# config/connectors/rest-mtls.yaml
plugin: rest
kinds: [price]
description: Prices from the pricing API over mutual TLS
settings:
  base-url: https://pricing.example.com/api
  header.Authorization: Bearer ${PRICING_TOKEN}
  tls:
    ca-file: /etc/drishti/tls/ca.pem
    cert-file: /etc/drishti/tls/client.pem
    key-file: /etc/drishti/tls/client.key
```

Check the service the way the connector meets it:

```
curl --cacert /etc/drishti/tls/ca.pem --cert /etc/drishti/tls/client.pem --key /etc/drishti/tls/client.key https://pricing.example.com/api/price/EURUSD
openssl s_client -connect pricing.example.com:443 -CAfile /etc/drishti/tls/ca.pem -verify_return_error < /dev/null
```

Once a certificate has under 30 days left, health reads `UP (TLS certificate CN=drishti (tls.cert-file) expires in 19 days
(2026-10-30))`.

| Message | Cause and fix |
|---|---|
| `tls.* is set but base-url is not https:// (…): use an https:// address` | `tls.*` keys with an `http://` URL |
| `tls.ca-file '/etc/drishti/nope.pem': file not found` | a wrong path; the message names the setting and the file |
| `SSLHandshakeException: … PKIX path building failed` | the service certificate is not signed by a CA in `tls.ca-file` |
| `HTTP/1.1 header parser received no bytes`, caused by `Connection reset` | the service requires a client certificate and none was configured |
| `No subject alternative names matching IP address … found` | the URL's host is not one the certificate names |

## Outbound proxy

The settings and rules are shared by every HTTP-based connector ([DATA_GUIDE.md section 10, proxy](../../../guides/DATA_GUIDE.md#outbound-http-proxy-for-connectors-ai-providers-and-mcp-servers);
keys in [CONFIGURATION.md](../../../admin/CONFIGURATION.md#shared-proxy)). A `proxy:` block in `settings:` (or `proxy: none`)
overrides the site default `drishti.http.proxy.*`; the password is an `${ENV}` placeholder, never a literal.

```yaml
settings:
  base-url: https://api.vendor.example/v1
  proxy:
    url: http://proxy.corp.example:3128
    username: svc-drishti
    password: ${PROXY_PASSWORD}
    no-proxy: [intranet.example]
```

Every request goes through the proxy (an `https://` `base-url` is tunnelled with `CONNECT` and keeps its `tls.*` end to end).
Health says so: `UP via proxy proxy.corp.example:3128 (connector)`, or `UP (proxy ... not used for api.example: no-proxy)`. A
refused login reads `the proxy proxy.corp.example:3128 refused the credentials (HTTP 407 Proxy Authentication Required): check
proxy.username and proxy.password`.

## Troubleshooting

| Symptom | Likely cause | What to do |
|---|---|---|
| `failedToStart: … rest plugin needs settings.base-url` | `base-url` empty or unset | set it (`DRISHTI_REST_URL` for the plugin as itself) |
| `lastError` `… answered HTTP 401` / `403` | token missing, expired, or a placeholder sent as text | check the header value in the server's environment; restart after changing it |
| `lastError` `… answered HTTP 400` for kinds the service does not know | the connector has no `kinds` and is asked for every kind | give it `kinds:` |
| `lastError` names `HttpConnectTimeoutException`, `ConnectException`, `UnknownHostException` | the service is unreachable from the server | `curl -i` the URL from the server host; check proxies and firewall |
| `lastError` names `SSLHandshakeException` / `PKIX path building failed` | the certificate is not trusted | `tls.ca-file` ([TLS](#tls-for-the-rest-connector)) |
| `lastError` names a JSON parse error | the service answered HTML (a login page, a redirect) | `curl -i` the built URL; point `base-url` at the final address |
| *No data available* | `2xx`/`3xx` with an empty body | the service must answer `404` for unknown ids |
| `DRS-1004 timed out reading …` | the service is slower than `fetch-timeout` | raise `fetch-timeout` and `timeout-ms` together, or route the kind to a faster store |
| the view always shows the lake's data, or a sample | the route names the lake, or the demo samples hold the same id | route the kind to the connector; `DRISHTI_DEMO_ENABLED=false` |
| type-ahead does not offer the id | the connector cannot search | type the whole id, or load the ids into a dated store |
| a new generation on every read | no numeric version header | set `generation-header` |
| `%2F` ids answer `404`/`400` | the service or a proxy refuses encoded slashes | put the id in the query string (`path: /lookup?key={id}`) |

A service that is down keeps health `UP`: watch `reads.errors` and `lastError` in Admin → Health. To see the request the
connector sends, build it by hand (`<base-url without trailing slashes><path with {kind} and {id} encoded>`) and
`curl -i -H 'Accept: application/json' -H 'Authorization: Bearer …' <url>`.

## Checklist for production

1. A named connector with `kinds:` listing exactly the kinds the service holds.
2. The service answers `404` for an unknown id, `200` with a JSON object for a known one, and no redirects at the configured address.
3. A numeric version header, named in `generation-header`.
4. The token in the environment, with no default; check the first read after each deploy.
5. For `https` a trusted CA (`tls.ca-file`); for mutual TLS a client certificate.
6. `timeout-ms` below `drishti.sources.fetch-timeout`, with room for connectors tried before it.
7. Decide who answers Live and who answers picked dates, set the route, switch the samples off.
8. For type-ahead, search, history or impact, load the kind into a dated store as well.
9. Check the service carries one request per view open plus one per linked entity at the busiest hour.
10. Alert on `reads.errors` and `lastErrorAt`: health stays `UP` while the service is down.
