## Medium
**M-1 Approving a design overwrites an existing live version in place.** `design_propose` of a design whose Sutra says `version: 2` when `book@2` already exists in the Studio directory is accepted (202), approved (200) and **rewrites book@2** (its source now holds the new text; the design shows `live(v2)`, the list still says latest 2). The same name@version in a pack directory is refused, but only at *approval* (`422 DRS-2028`), after the proposal was accepted: the design stays `proposed(P-n)` and the proposal pending forever. The guide promises "the next version"; nothing bumps the number. Where: `SutraGovernance.propose/approve`, `DesignShip`, `SutraRegistry.java:160,283`. Repro: `scripts/rebase.py` (second half), then re-run the tail of the script with base `book@2`.

**M-2 No rebase when the base Sutra moves.** BUILD_WORKBENCH "Core object" says operations replay when the base version moves and conflicts show as problems. Nothing does: after `book@2` went live, a design with `base: book@1` kept `base: book@1`, no flag, no replay, no problem; proposing it collides (M-1). Where: `DesignService`/`DesignController` (no code mentions the base after creation). Repro: `scripts/rebase.py`.

**M-3 Integers beyond 2^53 make the shape's schema reject its own samples.** `minimum`/`maximum` are written as doubles: `12345678901234567890123` > `1.2345678901234568e+22`, `Long.MAX_VALUE` < its own `minimum` 9.223372036854776e18. With such values in the samples, 148 of 300 random sets produced a schema that fails exact validators (python-jsonschema). `1e999999` is written as `"minimum": "Infinity"` (a string, not a valid JSON Schema). Where: `SchemaWriter.java:173-174`. Repro: `scripts/shape_hostile.py nums_big num_huge_literal`; `BIG=1 python3 scripts/shape_fuzz.py 1 300`. **Fixed** in 69343448 (ShapeMergeRulesTest.integersBeyondTwoToThe53AreWrittenExactlyAndNonFiniteNumbersAreOmitted, ShapePropertyTest with big and non-finite numbers).

**M-4 Sparse optional sections become a "map", even at the root.** Four object-typed sections that appear in at most half of the documents (`rates`/`fx`/`credit`/`equity`, one per document) are detected as a map of ids (`keysVary`), so the *whole document* becomes `map` and the sections' fields are merged into one value schema (`$ {} {}` integer). Same for months present in subsets. Auto-design then has nothing to name. Where: `ShapeMerger.detectMap` (lines 76-92: `keysVary` has no minimum on document count or key-name shape). Repro: `scripts/shape_map.py`. **Fixed** in 69343448 (ShapeMergeRulesTest.sparseOptionalSectionsStayARecordNotAMap, datesAsKeysAreAMap).

**M-5 Export then import grows the notes every cycle and renames samples.** The README (with the original notes embedded) is imported as the notes: +567 characters per export→import cycle (564, 1131, 1698 ... 2832 after five). Sample names are rewritten (`é.json`→`_.json`, `名.json`→`_-2.json`, `a/b`→`a_b.json`, `sample`→`sample.json`, `sample.json`→`sample-2.json`, non-ASCII collapses to `_`). Sutra text and sample documents are byte-equal after the round trip, the re-export differs only in `pack.yaml`/`README.md` (design id). Where: `PackFragment.java:236` (readme embeds notes), import reads the README as notes. Repro: `scripts/roundtrip.py`. **Fixed** in 1615c22f (DesignShipApiTest.exportThenImportKeepsTheNotesAndTheSampleNamesAcrossCycles).

**M-6 CLI `sutra test` writes no JUnit file when a sample is unreadable.** An invalid or BOM-prefixed JSON sample ends the run with exit 1 and `--junit` is never written, so a CI "publish test report" step finds nothing (and a failure without a report cannot be told from a crash).
