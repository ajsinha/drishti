# 2.6.5 documentation verification

The documentation part of the 2.6.5 adversarial QA ([QA_PLAN.md section 6](QA_PLAN.md#6-documentation-verification-30-minutes-during-the-fix-run)),
in the format of [the 2.3.0 verification](../2.3.0-docs-verification.md). One row per document touched since `v2.5.0`
(`git log --name-only --format= v2.5.0..HEAD -- docs README.md data/testdata/README.md | sort -u`, on `develop` at fcd4e351c), plus the
pages found wrong by the cross-checks that were not touched (FEEDS_CONNECTOR) and the release documents (CHANGELOG, RELEASE_NOTES).
Pictures and tutorial data files are grouped one row per folder. Reviewed 2026-10-20.

## How to use this table

- Pick a row; open the page in the help centre (the address in brackets) beside your QA stack: the quick start of
  `data/testdata/README.md` on the sixty-day demo lakes, signed in as `drishti-dev-admin`, with a personal API token in `DRISHTI_TOKEN`.
- **Outcome** values: *new* (added since 2.5.0); *wrong → fixed* (this review found it wrong and fixed it, commit d8ce06790);
  *updated* (changed in this review without being wrong); *verified* (read against the code, configuration or another page named in the
  row, no change needed); *names-only* (only names, paths or version strings changed since 2.5.0; nothing else re-verified).
- **This review ran no server.** *Verified* means read against the code and configuration named in the row (`TokenScopes`,
  `application.yaml`, `config/help.yaml`, `config/packs/trading/pack.yaml`, `tools/lake/demo.py`, `data/testdata/testdata.yaml`, the
  `drishti.py … --help` output, `plugins/`); where a row says *commit message*, the builder's check is not repeated. The QA rounds
  ran the commands of the history, statement and net pages on their stacks ([QA1](QA1_FINDINGS.md), [QA2](QA2_FINDINGS.md)).
- **Waits for fix QAx-nn**: the page describes behaviour the QA found broken; it is left as it is until the product is fixed.
- **Commit**: the latest commits that touched the file (`git show <commit> -- <file>`); d8ce06790 is this review's fixes.

## The sixty-day test data

The test data holds **sixty business days** since 2.6.5 (`data/testdata`, the test data's 2026-07-08 to 2026-09-30; was seven). The
real build: `Demo lake ready: …: 64 tables, 60 business days 2026-07-08 to 2026-09-30, 943 s` (a run that kept the test data's dates;
by default `lake demo` moves the days to end on today's business date), about 15 minutes and 2.2 GB. The pages that showed the
seven-day output now show this summary line and leave out the seven-day per-table row counts. Where a page's captured figures
(counts, values, dates) come from the seven-day lakes of 2.5.0 and were not re-captured, the page says so; no new figure was made up.

- **Ids for history** (ten amendments each in the sixty days): ENDUR `1000279`, `1001049`; CALYPSO `CLY-4000509`; MUREX `MX-30001745`.
- **`MX-20000001`**, the tutorials' sample MUREX swap, is **cancelled** part-way: version 7, `TRADE_STATUS: CANCELLED`, in the test
  data's 2026-09-22 change file, so its last seven business days read `CANCELLED`. Notes were added where a page shows it live or shows
  its status (tutorials README, 01, 02, 21; RACHANA_REFERENCE; SUTRA_DEVELOPER_GUIDE). HOW_IT_FITS and DEMO_DATA show the demo sample
  and the generator's document, which are not the lakes, and are left.
