# 2.3.0 documentation verification

Every guide, help-centre page and tutorial of 2.3.0, checked against the running product on a **fresh clone** built exactly as
[data/testdata/README.md](../../data/testdata/README.md) says: clone, install, build the server jar, `drishti.py lake demo` (seven business days
ending 2026-10-16: 15,000 trades from ENDUR, CALYPSO and MUREX, 15,000 trade valuations, 64 tables), then the server with the settings of the
run configuration *Drishti server (demo lakes)* (sign-in on, the development administrator `drishti-dev-admin`) and the console of *Drishti console*.
Tutorials 12, 15 and 16 also ran with the demo ticker, the AI mock provider and embedding on, as their prerequisites say; tutorial 11's mail step
with a local SMTP sink. Done on 2026-10-17, branch of the 2.3.0 accuracy pass.

## How to use this table

- **Document** names the page and its address in the help centre (`/help/...` on your console): open it beside your QA stack.
- **Outcome**: *rewritten* (written again for the current product), *updated* (corrected where it was wrong, the rest checked), *verified*
  (checked, nothing was wrong). A page marked *reviewed* could not be run here (it needs systems this machine does not have) and was read
  against the code.
- **What was checked**: what was actually done: steps followed, commands and API calls run with their output pasted in, pictures retaken.
- **Commit**: where the change is (`git show <commit>`).
- **How to re-check** is one action you can do in a few minutes on your own QA stack (the quick start of data/testdata/README.md, signed in as
  `drishti-dev-admin`, with a personal API token in `DRISHTI_TOKEN` for the command lines). Figures from the lakes are of business date
  2026-10-16; a lake built on another day keeps the same counts but moves the dates.

## Found and not fixed (for the lead)

1. **Trade pages are slow on the lakes**: `counterparty-trades` and `portfolio-trades` read every member trade's document one id at a time (up to
   20,000 reads); `CP-MERIDIAN-RE` timed out (DRS-1004) under load and `BOOK-COMM-1` ran a 3 GB server out of memory (4 GB, the run configurations'
   size, held). The pages should read promoted columns.
2. The feed plugin writes camelCase documents (`indexId`, `fixings`); the market-data Sutras read UPPER_SNAKE, so a feed entity's view is empty
   (CONNECTOR_FILES and FEEDS_CONNECTOR say so).
3. JDBC query mode turns UPPER_SNAKE column labels into camelCase; the DuckDB loader types a column from its first value (`TRADE_ID` DOUBLE, text ids
   NULL); `config/connectors.examples/*/trading-store.yaml` are still the single 2.2 trade connector.
4. Derived kinds write camelCase `derivedFrom`, `memberCount`, `dealsIds`.
5. Load verification counts the newest listing, not the date asked: a load for a date the lake does not have is `verified`.
6. CSV export writes large numbers as `4.1087E9`; a refresh of one dataset reports its rows twice (30,000 for 15,000).
7. Python visuals and Analyse extracts stop at 10,000 rows (15,000 on the lakes) with only a small note.
8. The words parser reads `negative mtm, top 10` as the largest ten; the *condition ends early* message suggests `mtm > 1m` in lower case; the deal
   page's function-key labels are cut mid-phrase (`Cash-flow schedule,`).
9. Deleting a pack folder leaves it in `<data>/packs/added.yaml`, and then the headless Sutra tools refuse to run in that checkout; `sutra lint`
   writes an identity database into the data folder it runs in.
10. `pack make` picks `START_DATE` as the business date of production-shaped snapshots; auto-design gives a kind whose id it reads as a link a literal
    title (`'ticket'`).
11. The example schemas under `docs/guides/examples/schemas/` are camelCase (23 assertions of `test_schemakit.py` follow them).
12. `drishti.py doctor --server URL` still probes the local 18480 and 17480.
