# 2.3.0 documentation verification

One row per document of `docs/guides`, `docs/admin`, `docs/connectors` and `docs/tutorials` (the help centre renders each of them; its address is in
brackets). Outcomes are derived from the git history since `v2.2.0` (`git log --oneline v2.2.0..HEAD -- <file>`), not from memory: the **Commit**
column is where to look, and **What was checked** repeats only what that commit (or the names-only pass on 2026-10-17) says it did. Where a row says
*commit message*, the check was done by the builder of that commit and is not repeated here; where it says *names-only*, only names were
changed and no behaviour was re-verified.

## How to use this table

- Pick a row; open the page in the help centre (the address in brackets, on your console) beside your QA stack: the quick start of
  `data/testdata/README.md`, signed in as `drishti-dev-admin`, with a personal API token in `DRISHTI_TOKEN` for command lines.
- **Outcome** values: *rewritten* (a large part of the text changed, written against the current product); *updated* (corrected where it was wrong);
  *verified* (checked with at most a few lines changed); *names-only* (field, pack and connector names changed in the examples, nothing else
  re-verified); *unchanged since 2.2.0* (no commit; not re-checked); *new in 2.3.0*.
- **Commit**: the latest commits that touched the file (`git show <commit> -- <file>`).
- **How to re-check**: one action of a few minutes on the QA stack. If what you see differs from the page, the page is wrong: report the row.
- Figures taken from the demo lakes are of the business date the lake was built for; counts stay, dates move.
