# The redis connector

Plugin `redis` (`plugins/drishti-plugin-redis`): a million trades a day in memory, a trade in about 5 ms, searches over a day in
80 to 250 ms, and live updates pushed to open views. Redis holds the recent days; Delta Lake or Iceberg behind it holds the years,
and Drishti asks that store for any date Redis does not hold.

## What it reads

A data domain (`trading`) is a key prefix. The kinds come from `<domain>:kinds`, each kind's days from a sorted set, an entity's
document from one `GET` (or one `MGET` over its candidate days), and a day's promoted fields from one hash read field by field. Days
are replaced atomically through generations, so a reader sees a whole old day or a whole new one. With `live: true` (the default) it
subscribes to `<domain>:changes` and re-reads an open entity, or refreshes the catalogue for a whole day. Retention is a TTL on every
key (`--ttl-days`). It never writes; `tools/load-redis.sh` (`RedisLoader`) does.

## Data structure

Braces are Redis Cluster hash tags (keys sharing the text between `{` and `}` share a slot):

| Key | Type | Holds |
|---|---|---|
| `trading:kinds` | SET | the kinds the domain holds |
| `trading:trade:days` | ZSET | the kind's business days (member and score `yyyyMMdd`) |
| `{trading:trade:days}:gens` | HASH | each day's current generation (`yyyyMMdd` → `<g>`) |
| `trading:trade:{MX-20000017}` | ZSET | the entity's business days |
| `trading:trade:{MX-20000017}:20260930.<g>` | STRING | the entity's document that day, compressed (`…:20260930` without a generation) |
| `{trading:trade:20260930}:cols:<g>` | HASH | the day's ids and promoted fields, column-wise in chunks of 10,000 (`meta`, `#id:<n>`, `<PATH>:<n>`) |
| `trading:trade:dict`, `trading:dict:<id>` | STRING | the kind's current zstd dictionary id, and the dictionary (never delete these) |
| `trading:updated` | STRING | when a loader last finished (epoch milliseconds) |
| `trading:changes` | channel | `kind TAB id TAB yyyyMMdd` (id `*` for a day's columns) |

- **Id rule:** the entity id is the hash tag in `<domain>:<kind>:{<id>}`; its document key adds `:<yyyyMMdd>.<generation>`.
- **Document compression,** by the first byte: `{` or `[` plain JSON (any writer may store this), `1` Deflate, `2` zstd, `3` a 4-byte
  dictionary id then zstd (the loader's default, about 820 bytes a trade).
- **Column chunks:** `D` numbers (transposed doubles), `T` texts with few distinct values (a dictionary and indexes), `P` other texts;
  a path whose values are all numbers is a number column, anything else text.

## Examples

```yaml
# config/connectors/trade-endur.yaml
plugin: redis
kinds: [trade]
settings:
  domain: trading                         # the key prefix trading:…
  uri: ${DRISHTI_REDIS_URI:redis://localhost:6379}      # rediss:// for TLS; several, comma separated, for Cluster seeds
  cluster: ${DRISHTI_REDIS_CLUSTER:false}
  password: ${DRISHTI_REDIS_PASSWORD:}
  layout.trade.columns: TRADE_ID,SOURCE_SYSTEM,PRODUCT_TYPE,CURRENCY,QUANTITY,COUNTERPARTY,PORTFOLIO
```

Ready-made files for the six banking domains: `config/connectors.examples/redis/`. Load data with
`tools/load-redis.sh redis://localhost:6379` (add `--trades N --days D`, `--ttl-days N`, `--merge` to add to a day, `--publish` to
announce changes to open views).

## Troubleshooting

- `DOWN: cannot reach Redis at redis://…`: Redis unreachable, wrong URI or credentials; check `uri`, `user`/`password`, `rediss://`.
- `…; reads fail at once until it answers (checked every 1000 ms)`: Redis is known to be down (`fail-fast`); the connector recovers
  by itself.
- `tls.* is set but uri is not rediss://: use rediss://host:port for Redis over TLS`: use `rediss://` and the TLS port.
- `zstd dictionary … is missing`: a `<domain>:dict:*` key was deleted; reload the affected days.
- A new day is not served: its load has not finished (columns are written at the end).
- Open views do not tick: the writer does not `--publish`, or `live: false`.
- Loader `OOM command not allowed when used memory > 'maxmemory'`: Redis is full; shorter `--ttl-days`, more memory or shards.

Every health text is in the full document, section *Diagnosing*.
