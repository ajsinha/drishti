# The cassandra connector

Plugin `cassandra` (`plugins/drishti-plugin-cassandra`): one entity in a few milliseconds, type-ahead from memory and searches over a
day's promoted columns, from a keyspace that `tools/load-cassandra.sh` (or any writer keeping the same layout) fills.

## What it reads

A data domain (`trading`) is a **keyspace**; each kind is one table, one row per entity per business day, the whole JSON document in
`doc` plus the promoted fields as narrow columns. The kinds are learnt from the schema (each table's comment `drishti kind: <kind>`),
never by scanning. It is read-only: its role needs `SELECT` on the keyspace.

| Store | Works | Notes |
|---|---|---|
| Apache Cassandra 4.0, 4.1, 5.0 | yes | Cassandra 5 is tested (the dated-source contract, the loader, TLS, equality with Delta Lake) |
| ScyllaDB | yes | the same protocol and CQL; ScyllaDB 6.2 is tested with the dated-source contract |
| DataStax Astra / DSE | yes | through its secure connect bundle and a token (`secure-connect-bundle`, `token`) |
| Amazon Keyspaces | wired, not yet checked | SigV4 log-in through AWS's driver plug-in (`sigv4: true`), TLS required, `LOCAL_QUORUM` |
| Azure Cosmos DB for Apache Cassandra | expected | not checked |

No secondary index is used (SAI or otherwise): every read names a whole partition key and searches run on columns in Drishti, so the
connector behaves the same on every store above. The engine side (columns, searches, derived kinds, impact) is shared with Delta Lake
([the delta connector](../drishti-plugin-delta/README.md)). The settings are also summarised in
[CONFIGURATION.md › Connector settings](../../docs/admin/CONFIGURATION.md#cassandra).

## Data structure

The expected layout (the loader writes it with `--create`):

```sql
CREATE TABLE "trading"."trade" (                         -- one table per kind; netting-set becomes netting_set
    "business_date" date, "generation" int, "bucket" smallint, "id" text,
    "doc" text,                                          -- the whole JSON document, exactly what a view shows
    "trade_id" text, "portfolio" text, "quantity" double, "legs__currency" text,   -- promoted fields (layout.<kind>.columns)
    PRIMARY KEY (("business_date", "generation", "bucket"), "id")
) WITH comment = 'drishti kind: trade';

CREATE TABLE "trading"."entity_days" ("kind" text, "id" text, "business_date" date,
    PRIMARY KEY (("kind", "id"), "business_date")) WITH CLUSTERING ORDER BY ("business_date" DESC);

CREATE TABLE "trading"."kind_days" ("kind" text, "business_date" date, "generation" int, "buckets" int, "rows" bigint,
    "loaded_at" timestamp, PRIMARY KEY ("kind", "business_date")) WITH CLUSTERING ORDER BY ("business_date" DESC);
```

- **Id rule:** the `id` clustering column is the entity id; one entity is one row of one partition, and a partition's ids come out
  sorted.
- **A partition per day per bucket.** Cassandra wants partitions well under 100 MB. A day's rows are spread over `buckets` partitions
  (128 by default) by `murmur3(id) mod buckets` (Murmur3 x86 32-bit, seed 0, of the id's UTF-8 bytes: any client can compute it). A
  million trades of about 7 KB in 128 buckets is about 7,800 rows and 55 MB a partition. The bucket count is recorded with each day in
  `kind_days`, so it can grow for a larger book without touching old days.
- **Document:** `doc` holds the JSON document as the pack's kind defines it (for `trade`: `LEGS[].CASH_FLOWS[].RESETS[]`, `EVENTS[]`,
  see the trading pack's README); nested lists stay inside the document. New tables use `ZstdCompressor`.
- **Promoted columns:** a path `LEGS.CURRENCY` is the column `legs__currency` (lower case, other characters `_`; a name longer than 48
  characters is cut and given 4 hex digits of its SHA-1; `id` or `doc` as a path becomes `f_id`, `f_doc`). Numbers are `double`,
  everything else `text`. They let searches, pick lists, derived kinds, impact and reverse lookups read a day's few narrow columns and
  never the documents.
- **Which fields are columns** is declared by the pack on the connector that stores the kind (`layout.<kind>.columns`), exactly as for
  Delta Lake and Aerospike. The loader takes the promoted values from its input (`columns` in each JSON line), so the connector and the
  loader agree as long as both come from the pack. A path the table has no column for is not offered as a column (searches on it read
  documents). Effective kinds are never read as columns (their days hold changes only).
- **Generations:** `generation` is part of the partition key so that a reload writes new partitions beside the old ones; a day appears
  whole or not at all, and readers follow `kind_days`, which names the generation to read ([Loading](#loading)).
- **The table comment** `drishti kind: <kind>` names the kind a table holds (`netting-set` becomes the table `netting_set`).

## Examples

```yaml
# config/connectors/trade-endur.yaml
plugin: cassandra
kinds: [trade]
settings:
  domain: trading                                   # the keyspace
  contact-points: ${DRISHTI_CASSANDRA_CONTACT_POINTS:localhost:9042}
  local-datacenter: ${DRISHTI_CASSANDRA_DATACENTER:datacenter1}
  username: ${DRISHTI_CASSANDRA_USERNAME:}
  password: ${DRISHTI_CASSANDRA_PASSWORD:}
  layout.trade.columns: TRADE_ID,SOURCE_SYSTEM,PRODUCT_TYPE,PORTFOLIO,COUNTERPARTY,CURRENCY,QUANTITY
```

The `username` and `password` defaults are empty, which is a development node with no sign-in: set both for a node that asks for
one. Ready-made files: `config/connectors.examples/cassandra/` (the six banking domains; `trade-endur.yaml` replaces the trading pack's
Delta connector of that name and serves every system's trades the loader wrote), `other/cassandra-tls.yaml` (mutual TLS) and
`other/cassandra-astra.yaml` (Astra). Copy them to `config/connectors/` (or create one in Admin → Connectors → New, plugin
`cassandra`); the server picks the files up without a restart.

**Walk-through on a development node:**

1. Run Cassandra: `docker run -d --name cass -p 9042:9042 cassandra:5.0.6` (ScyllaDB: `scylladb/scylla:6.2 --smp 1
   --developer-mode 1`). Wait until `cqlsh` answers.
2. Load the samples and a small book: `tools/load-cassandra.sh localhost:9042 datacenter1 --create --create-keyspace 1 --trades 10000
   --days 3`. The last line reads `cassandra: loaded … rows (… days)`.
3. `cp config/connectors.examples/cassandra/*.yaml config/connectors/`.
4. Check: Admin → Connectors → `trade-endur` → **Test connection** lists the days and their rows; Admin → Health says `UP`.
5. Use it: `TRD ` in the command line offers the trades; open one; a search such as `TRD PORTFOLIO=BOOK-RATES-3` reads the day's
   columns.
6. Reload a day with the same command: readers switch to the new generation when the load ends, never seeing half a day.

If the Delta `trade-endur` is disabled and the Cassandra file has another name (`trading-store`), the kind is still read from it; an
id it does not hold answers `DRS-1001 no source holds trade/… (asked trading-store; trade-endur, which kind 'trade' is routed to, is
disabled)`.

## Troubleshooting

Admin → Health shows the connector; Admin → Caches its figures (`kinds`, `daysIndexed`, `ids`, `columnSets`, `documents`); Admin →
Connectors → the connector → Pool its connections.

`DOWN: connecting to Cassandra at …` means the driver cannot open a session. The connector starts anyway and the driver keeps trying in
the background; the connector also opens one connection of its own to the first contact point (at most every 30 s) and adds what it
found after a colon. With nothing added, the node answers CQL: look at `local-datacenter` (`nodetool status`) and the log-in.

| Symptom | Likely cause | What to do |
|---|---|---|
| `… : no connection to <host:port> (ConnectException: Connection refused) …` | wrong `contact-points`, a closed port, the node down | `nc -z <host> 9042` |
| `… : TLS to <host:port> failed (…): the node asks for a client certificate (mutual TLS) and none is set …` | the node has `require_client_auth: true` | set `tls.cert-file` + `tls.key-file` (or `tls.keystore`) |
| `… : TLS to <host:port> failed (…): the node refused the client certificate …` | the client certificate is not signed by an authority in the node's truststore | a certificate from the node's authority, or add its CA to the node |
| `… : TLS to <host:port> failed (…): the node's certificate is not trusted …` | the connector does not trust the node's authority | `tls.ca-file` or `tls.truststore` |
| `… : TLS to <host:port> failed (…): the node's certificate does not name <host> …` | the host name check failed | connect by a name the certificate holds, or `tls.verify-hostname: false` |
| `… : TLS to <host:port> failed (…): the node does not speak TLS on this port …` | `tls.enabled: true` against a plain port | `tls.enabled: false`, or the TLS port |
| `… : TLS: the node at <host:port> did not answer CQL in plain text …, so it requires TLS` | no TLS against a node that demands it | `tls.enabled: true` with `tls.ca-file` (and the client certificate when asked) |
| `DOWN: keyspace … does not exist` | the keyspace is named after the domain unless `keyspace` is set | set `keyspace`, or load it |
| `DOWN: keyspace … has no kind_days table` | nothing was loaded in the connector's layout | `tools/load-cassandra.sh --create`, or run the printed CQL |
| `UP (2 of 3 nodes up)` | a node is down; reads go to the replicas left | the driver reconnects by itself |
| a new day does not appear | the catalogue is re-read every `refresh-seconds`; or the load failed before `kind_days` was written | wait, or Admin → Caches → purge; check the loader's last line |
| searches say `partial: true` | a field the query reads is not a promoted column | add it to `layout.<kind>.columns` and reload with `--create` |
| loader: `… does not exist: run the CQL above` | no `--create` | have an administrator run the printed CQL, or pass `--create` |
| loader: `retention would drop …` | `--keep-days` would drop more than half of the days | check the dates of the load, or pass `--force-drop` |
| loader warning `a partition holds about … MB` | `buckets` too low for the book | load with the `--buckets KIND=N` it names |

## How it reads

Every statement is prepared once and names a whole partition key; the driver routes it to a replica that owns the partition. Nothing
scans a table: no `ALLOW FILTERING`, no token range.

- **The catalogue.** Every `refresh-seconds` (60) the connector reads each kind's `kind_days` partition (a few hundred small rows for
  years of history). A kind's ids for type-ahead are re-read only when its newest day or that day's generation changed. The newest
  day's promoted columns are then read in the background, so the first search finds them ready.
- **One entity** (`TRD MX-20000017` on 2026-09-30): choose the day (a `snapshot` kind: its newest day on or before the date asked,
  within `lookback-days`, from the catalogue; an `effective` kind: the entity's latest day on or before it from `entity_days`, one
  read, the first the catalogue lists), then read one row by `business_date`, `generation`, `bucket` and `id`. A document read is kept
  in `doc-cache-mb`, keyed by the day's generation, so a reload is never served stale.
- **Type-ahead** comes from the ids of the newest day (an effective kind: of every day, at most `max-load-rows`), read bucket by bucket
  into a sorted in-memory index. A trade written after the last refresh is readable at once and offered after `refresh-seconds`.
- **A day's columns.** Searches, pick lists, derived kinds, impact and reverse lookups read a column set: the ids and promoted columns
  of every bucket of the day's generation, `scan-threads` partitions at a time and `page-size` rows a page; the document column is
  never selected. It is kept within `columns-cache-mb` per day and generation. A day the catalogue does not list (expired, dropped or
  never loaded) answers "not held", so the next connector for the kind is asked.
- **Reverse lookups** ("which trades reference netting set `NS-SUMMIT-NY`?") come from the day's promoted text columns; a kind without
  promoted columns reads that day's documents, at most `max-load-rows`. `reverse-index: false` turns them off.
- **Documents of a day, inventory, versions.** Derived pages read a snapshot kind's day in one pass, bucket by bucket. **Test
  connection** shows each day's row count from `kind_days`. The kind's data version (for the BI store) is its days and their
  generations, so a load of another day leaves a stored layer valid.
- **History** (`TRD 1000015 30`, [DATA_ARCHITECTURE.md](../../docs/architecture/DATA_ARCHITECTURE.md#2-history-queries-an-entity-over-time)):
  one single-partition range read of `entity_days`, keeping only days `kind_days` still names, then one document per day by its
  partition, eight at once. One generation is kept, so `versions` is 1 and *known at* is refused (`DRS-1007`).
- **Live changes.** The connector refreshes; it does not push. To push, put a Kafka connector in front of it.

## Loading

`tools/load-cassandra.sh` (Windows: `tools\windows\load-cassandra.ps1`; `drishti.py data load --store cassandra` runs it) loads the
packs' sample data and optionally a generated book through `CassandraLoader` (in the plugin):

```bash
tools/load-cassandra.sh localhost:9042 datacenter1 --create --create-keyspace 1                   # the samples x 10 days
tools/load-cassandra.sh localhost:9042 datacenter1 --create --trades 10000 --days 3               # and a book, streamed
tools/load-cassandra.sh cass1:9042,cass2:9042 dc-east --ttl-days 90 --setting tls.enabled=true \
    --setting tls.ca-file=/etc/drishti/tls/ca.pem --username loader --password "$PW"            # a secured cluster
```

The loader's heap is `DRISHTI_LOADER_HEAP` (default `4g`). The last line names the rows, the days and the rate
(`cassandra: loaded 30,000 rows (3 days) in 49.7 s (604 rows/s)`).

- **Input:** loader rows, one JSON line per entity per day: `{"domain", "kind", "id", "date", "doc", "columns": {path: value}}`, as
  `make_data.py --jsonl FILE.tar` and `bulk_trades.py --jsonl FILE.tar` write them (tars of `<kind>/<YYYY-MM-DD>/rows.jsonl`). A folder
  argument loads each `.tar`, `.tgz`, `.tar.gz`, `.jsonl` and `.jsonl.gz` in it, in name order.
- **Business dates come from outside the row**, by the load rules every loader shares
  ([DATA_LAKE_GUIDE.md, section 5](../../docs/guides/DATA_LAKE_GUIDE.md#5-routing-business-dates-modes-repeats-and-undo)): a tar's
  folder date; for a plain file (`<kind>.<YYYY-MM-DD>.jsonl[.gz]`, or `-`), `--as-of`, else its `.ready` file, else the date in its
  name, else the business today. A plain file of two kinds is refused (*send a tar*), and so is `--as-of` with a tar.
- **A day appears whole or not at all.** Each day of the input gets a new generation. The day's rows go to the new generation's
  partitions, then its `entity_days` rows, and only when every write has succeeded the `kind_days` row naming the new generation.
  Readers switch at that moment. The old generation's partitions are then deleted (`buckets` whole-partition deletes). If a write fails,
  no day of the load is switched.
- **Writes** are prepared statements at `LOCAL_QUORUM` (`--consistency`), at most `--in-flight` (256) at once, grouped per partition
  into unlogged batches of at most `--batch-rows` (32) rows or 256 KB, never across partitions.
- **`--create`** creates the tables (`IF NOT EXISTS`) and adds a column for a newly promoted field. Without it the loader prints the CQL
  for a database administrator and stops before writing. `--create-keyspace RF` creates a SimpleStrategy keyspace, for a development
  node only.
- **`--buckets N`** (128), or `--buckets KIND=N`, sets the partitions per day for new loads; the loader warns when a partition passes
  100 MB and names the value to use.
- **Dates are guarded:** a row dated after tomorrow in the business zone is quarantined and the load ends with an error once the good
  rows are in (`--future-days`, `--zone`).

**Your own loader** (a Spark job, a Kafka consumer) writes the same three things in the same order: the day's rows under a new
generation, the `entity_days` rows, then the `kind_days` row (`generation`, `buckets`, `rows`, `loaded_at`); then it deletes the old
generation's partitions. `CassandraLayout` has the CQL and the bucket function, and can be called from Java.

### Retention: TTL or dropped days

| Way | How | When |
|---|---|---|
| **TTL** | `--ttl-days N`: every data, `entity_days` and `kind_days` row is written `USING TTL`; with `--create`, new tables get `TimeWindowCompactionStrategy` with one-day windows, so whole SSTables expire together | a fixed retention; nothing to run |
| **Dropped days** | `--keep-days N`: after the load each loaded kind keeps its newest N days on or before the load's newest business date; older days' partitions and `kind_days` rows are deleted | a retention that changes; Amazon Keyspaces |

Dropping more than half of a kind's days needs `--force-drop` (`--max-drop-share`). Only whole partitions (and catalogue rows) are ever
deleted, so reads never wade through row tombstones; an `entity_days` row that outlives its day is passed over.

## Security

| Setting | Meaning for Cassandra |
|---|---|
| `tls.enabled: true` | TLS on (the cluster's `client_encryption_options`); `tls.*` without it is a start-up error |
| `tls.ca-file` / `tls.truststore` | trust the cluster's CA |
| `tls.cert-file` + `tls.key-file`, or `tls.keystore` | the client certificate, for `require_client_auth: true` |
| `tls.verify-hostname` | `true` by default: the node's certificate must name the address the driver connects to (the contact point, then each node's rpc address); `false` warns at every start |
| `username`, `password` | password log-in (`PasswordAuthenticator`); `password` is `${ENV}` or `file:` |
| `secure-connect-bundle`, `token` | DataStax Astra: the bundle carries the addresses, the data centre and TLS; the token is the password (user `token`) |
| `sigv4`, `sigv4-region` | Amazon Keyspaces: AWS's SigV4 plug-in (`aws-sigv4-auth-cassandra-java-driver-plugin`, not shipped: put its jar in the plugin folder) with the default AWS credential chain |

- **No HTTP proxy:** the native protocol is TCP; `proxy.*` settings are refused with that reason (use a TCP tunnel).
- **Roles:** the connector needs only `SELECT` on the keyspace; the loader `MODIFY` (and `CREATE`, `ALTER` with `--create`).
- **Connections:** `connections-per-node` per node, each carrying many requests; at most `max-concurrent-reads` in flight (further ones
  queue in the driver); `request-timeout-ms` per statement; speculative executions off unless `speculative-executions` is set (every
  read is idempotent). The Pool page shows connections open and busy. A client certificate's expiry within 30 days shows in Health.

## Sizing and limits

Estimates for a million trades a day, documents of about 7 KB compressing to about 1–1.5 KB with ZSTD:

| History in Cassandra | Rows | Data, one copy | With replication factor 3 |
|---|---|---|---|
| 90 business days | 90 million | about 110 GB | about 330 GB |
| 1 year (250 days) | 250 million | about 310 GB | about 0.9 TB |
| 7 years (1,760 days) | 1.76 billion | about 2.2 TB | about 6.6 TB |

Cassandra keeps its indexes on disk, so seven years needs disk, not memory. Most sites still keep **recent days in Cassandra and
history in a lake** (Iceberg or Delta Lake): configure the Cassandra connector first for the kind and the lake connector behind it; a
read or search on a day Cassandra does not hold falls through to the lake.

Memory in the Drishti server, per million trades: about 150 MB of type-ahead ids (the newest day), about 230 MB per day's column set of
19 fields (within `columns-cache-mb`), and `doc-cache-mb` of documents.

**Measured** at 10,000 trades a day with `CassandraScaleBench` (one Cassandra 5.0.6 node in Docker, 1 GB heap; 30,000 trade documents
of about 18 KB over three days; 128 buckets; 16 promoted columns; at the connector, medians): load 49.7 s (about 600 rows a second);
start with the catalogue and 10,000 ids ready 1.8 s; type-ahead under 0.1 ms; a trade's document 8.9 ms first, 0.2 ms cached, 4.9 ms on
a past day; a day's 16 columns 541 ms first, 0.1 ms again; a reverse lookup 8.7 ms; a day's 10,000 documents parsed 4.2 s; inventory
1.9 ms. A million trades a day and a multi-node cluster are estimates, not measured.

Limits:

- **No time travel** (*known at*): a read with `knownAt` fails with `DRS-1007` naming the connector.
- **Only promoted fields are fast**; others are searched in documents (20,000 at most, `partial`).
- **A stopped load leaves orphan partitions** (a generation `kind_days` never named). They are never read; they expire with a TTL, or
  delete them with `DELETE FROM <ks>.<kind> WHERE business_date = ? AND generation = ? AND bucket = ?` for each bucket.
- **Two loads of the same day at once** are not coordinated: the later `kind_days` write wins. Load a day from one place.
- **The first search on a day other than the newest** waits for that day's columns.
- **An effective kind's type-ahead** reads every day's ids (at most `max-load-rows`); keep effective kinds small.

### Checklist for production

- The keyspace created by an administrator with `NetworkTopologyStrategy` and the replication you need; the connector's role `SELECT`
  only, the loader's `MODIFY`.
- `buckets` sized so a partition stays well under 100 MB.
- TLS on, with certificates that name the addresses the driver connects to.
- Retention chosen: `--ttl-days` with time windows, or `--keep-days` from a scheduled load.
- One loader per kind and day; its exit status checked (a failed load switches nothing).
- A lake connector behind Cassandra for days older than it keeps.
- `local-datacenter` set to the data centre nearest the Drishti server; `consistency: LOCAL_QUORUM` unless staleness is acceptable.
