# The file connector

Plugin `file` (`plugins/drishti-plugin-file`): the simplest store Drishti reads. No database, no cluster, no service to run: each
business day of a kind is one file of JSON lines, which any tool can write and anyone can open in an editor. Right for a demo, a
nightly export or reference data kept by hand; for a million entities a day kept for years use Delta Lake or PostgreSQL.

## What it reads

`<root>/<domain>/<yyyy-MM-dd>/<kind>.jsonl` files (and undated `<root>/<domain>/<kind>.jsonl`, the same for every date), listed every
`rescan-seconds` (30). The first read of a day indexes it (ids, line offsets and promoted fields); the newest day is indexed in the
background, older days on first use, and a changed file is re-indexed when next read. Kinds are `snapshot` or `effective`
(`mode.<kind>`). It also reads the older layout of one file per entity (`<root>/<kind>/<id>.json` or `.csv`, CSV deprecated: logged once per file and named in health, dated
`<root>/<yyyy-MM-dd>/<kind>/<id>.json`), as the public-data feeds use. No time travel: a *known at* read is refused with `DRS-1007`.
It never writes; `tools/load-files.sh` (`JsonlLoader`) does.

## Data structure

```
<root>/trading/2026-09-30/trade.jsonl         every trade of 30 September, one per line, any order
<root>/reference/2026-09-30/counterparty.jsonl
<root>/reference/desk.jsonl                   undated: serves every date
```

A line is one JSON object, in either form (a file may mix them):

```json
{"domain": "trading", "kind": "trade", "id": "MX-20000001", "date": "2026-09-17",
 "doc": "{\"SOURCE_SYSTEM\": \"MUREX\", \"TRADE_ID\": \"MX-20000001\", …}",
 "columns": {"TRADE_ID": "MX-20000001", "QUANTITY": 242000000.0, "PORTFOLIO": "BOOK-RATES-3"}}
{"BOOK_ID": "BOOK-RATES-3", "NAME": "Rates book 3", "DESK": "DESK-RATES", "CURRENCY": "USD"}
```

- **The loaders' row** (what `make_data.py --jsonl`, `bulk_trades.py --jsonl` and every Drishti loader read and write): `doc` is the
  document (a JSON string or an object); `columns` carries the promoted fields (`layout.<kind>.columns`) so they are indexed without
  reading the document; without `columns` they are read from `doc`. The row's own `date` does not decide its day: the loader files it
  under its folder's or file's date ([the load rules](../../docs/guides/DATA_LAKE_GUIDE.md#5-routing-business-dates-modes-repeats-and-undo)).
- **A plain document:** the id is the field named by `id-field` (`id` by default; `BOOK_ID` above); promoted fields are read by path.
- **Id rule:** one entity per id per day; when an id repeats, its **last** line is the entity, as a reload would leave it (view,
  searches, derived kinds and reverse lookups all read that line); repeats are counted (`duplicateIds`) and named in health.
- **`NaN` and `Infinity`** (Python's `json.dumps` default) are read as no value: a promoted number is empty, so `QUANTITY < 0` does not
  match it and sums leave it out; the document holds `null` there.
- **A promoted field of mixed types** (a number on most lines, `"N/A"` on others; ENDUR's numeric `TRADE_ID` beside CALYPSO's text ids)
  keeps each value as the document holds it: numbers order before text, comparisons and sums treat them exactly as a document read
  would, and `1e20` stays `1e20`.
- **Unreadable lines** (truncated, not an object, no id, longer than `max-document-mb` or nested deeper than `max-nesting-depth`) are
  skipped, counted with their line number and why, logged once per version of the file and named in health; the rest of the day is
  served and searches over it say `partial` with the reason. (A row with `columns` is indexed without parsing its `doc`; a `doc` that
  itself breaks a limit serves searches from its columns and fails to open with the limit named.)
- **Promoted fields** are declared by the pack on the connector that stores the kind (`layout.<kind>.columns`, chosen as for every store:
  [PACK_DEVELOPER_GUIDE.md, Large kinds](../../docs/guides/PACK_DEVELOPER_GUIDE.md#large-kinds-the-lake-layout)); the `files` profile (`SPRING_PROFILES_ACTIVE=files`) switches the
  banking packs' store connectors to this plugin and keeps their settings. The trades are read per source system (`trade-endur`,
  `trade-calypso`, `trade-murex`), which the profile does not rename: point files at the trades with connector files of those names.

## Examples

```yaml
# config/connectors/trading-store.yaml
plugin: file
kinds: [trade]
settings:
  root: ${DRISHTI_FILES_ROOT:${drishti.data.dir:./data}/files}
  domain: trading                     # reads <root>/trading
  layout.trade.columns: TRADE_ID,SOURCE_SYSTEM,PRODUCT_TYPE,CURRENCY,QUANTITY,COUNTERPARTY,PORTFOLIO
```

Ready-made files for the six banking domains: `config/connectors.examples/files/`. Load the samples with `tools/load-files.sh` (add
`--trades 10000` for a generated book). Writing files yourself needs no loader: write `<kind>.jsonl.tmp` and rename it into place.

## Troubleshooting

`GET /api/v1/admin/health` gives the connector's figures:

```json
{"name": "trade-endur", "health": "UP", "cache": {"jsonlKinds": 1, "jsonlDays": 10, "indexedDays": 1, "ids": 10000,
 "indexBuilds": 1, "unreadableLines": 0, "duplicateIds": 0, "unreadableFiles": 0}}
```

A file with problems keeps the connector `UP` and names the file (the three newest such files, then a count), and is logged once as a
warning each time it is indexed: `UP (1 unreadable line in trading/2026-09-30/trade.jsonl (line 201: Unexpected end-of-input in
VALUE_STRING); 3 duplicate ids in trading/2026-09-29/trade.jsonl, the last line of each kept (MX-1, MX-2, MX-3))`.

| Symptom | Likely cause | What to do |
|---|---|---|
| `DOWN: no directory …` | the root (or `<root>/<domain>`) does not exist, or a share is unmounted | create it, or fix `root`/`DRISHTI_FILES_ROOT`; reads work again at once when it returns |
| a new file is not served | the next rescan has not run | wait `rescan-seconds` (30) |
| a kind is missing from type-ahead | its file cannot be read, or its lines have no id field | see health; set `id-field` for plain documents |
| health: `unreadable lines in …` | lines truncated, not JSON objects, without an id, or beyond `max-document-mb`/`max-nesting-depth` | fix or rewrite those lines, or raise the limit; the day is served without them, searches say `partial: true` with the reason |
| health: `duplicate ids in …` | an id on several lines of one day | the last line is served; write each id once |
| health: `unreadable file …` | the file cannot be opened (permissions) | fix it; it is read again when it changes |
| views of a date fail with `DRS-1003 <connector> failed reading …` | that day's file is there but cannot be opened | fix the file; the read is not passed to a store behind this one (a day's file that is gone is *not held*, and the next store answers) |
| searches say `partial: true` | a field the query reads is not promoted | add it to `layout.<kind>.columns`, and to the rows' `columns` |
| the first read of an old day is slow | the day is being indexed | expected once; raise `index-cache-mb` to keep more days |
| a *known at* read fails with `DRS-1007` | files keep no history of a day | use a store with time travel (Delta Lake) |

## How it reads

- **Finding the files.** Every `rescan-seconds` the domain folder is listed (dated folders, their `.jsonl` files, the undated files);
  no file is opened.
- **The index of a day.** The first time a day's file is needed it is read once into an index: every id, sorted, with the byte offset and
  length of its line, and the kind's promoted fields as columns (numbers as `double[]`, text as `String[]` with repeated values shared).
  The file is cut at line ends into up to 8 segments (one per 64 MB) indexed at once, each read in 4 MB blocks; a line's envelope is
  parsed without its document. Indexes are kept within `index-cache-mb` and rebuilt when the file is replaced or its size or modification
  time changes; the newest day of every kind is indexed during the rescan, in the background. An index is kept even for a file with
  unreadable lines or one that could not be opened, so it is read again only when it changes; a cache purge forgets every index.
- **Opening one entity** (`TRD MX-20000017`): a binary search of the sorted ids gives the line's offset and length, and one positioned
  read returns that line, however large the file. The index keeps its file open, so a file replaced by a rename is served whole from
  the old file until the next read sees the change; a file rewritten in place is caught by checking the line read is the id asked for,
  then re-indexed and read again. Each cached day counts at least 1 MB against `index-cache-mb` (so at most 1,024 open files by
  default).
- **Type-ahead** answers from memory: the newest day's ids of every kind (all days' ids for effective kinds). With `index.days: 5` (and
  `index.storage: mmap` for a lake searched often by past date) a past date's type-ahead answers from that date's own ids
  ([ARCHITECTURE.md, Several business days](../../docs/architecture/ARCHITECTURE.md#91-several-business-days)); a folder or file whose
  modification time changes is a restated day, rebuilt at the next rescan, and a silent restatement is caught every
  `index.reload-every`; **Admin → Connectors → this connector → Index** reloads a day by hand
  ([OPERATIONS.md, sizing the index](../../docs/admin/OPERATIONS.md#122-sizing-the-multi-day-type-ahead-index)).
- **Searches, pick lists, derived kinds and impact** read the day's promoted columns, exactly as on Delta Lake: exact over every entity
  of the day (`partial: false`), no document read. Other fields read documents (20,000 at most, then `partial`). A day whose file
  cannot be read at all is a failure, not *not held*: reads fail with `DRS-1003`, searches are `partial` naming the connector, and
  another store's data is not used in its place.
- **Reverse lookups** ("which trades reference `NS-SUMMIT-NY`?") come from the promoted text columns; a kind without them is answered by
  reading at most `max-load-rows` lines. An `effective` kind is looked up in each entity's version on the date (newest day first, each
  entity only in its newest line). Impact (F8) therefore works from files as from any store.
- **In a cluster** (Drishti*net) each kind names its table `file:<folder>#<fingerprint>`, a SHA-256 of the kind's files (path, size,
  modification time) taken at each rescan. Two servers reading the same folder say the same and are replicas; files that differ make them
  shards ([OPERATIONS.md, the capability digest](../../docs/admin/OPERATIONS.md#5-what-each-node-offers-the-capability-digest)). A kind
  with no file is not listed in the server's capability digest.

## Dates: snapshot and effective kinds

| `mode.<kind>` | Meaning | A read on a date |
|---|---|---|
| `snapshot` (default) | every entity every business day | the kind's newest dated file on or before the date (within `lookback-days`); an entity not in it is gone; else the undated file |
| `effective` | a line only when an entity changes | the entity's line in the newest file on or before the date that holds it |

A date older than every file (or beyond the lookback) is not held, so the next store configured for the kind is asked: recent days can
come from files and older ones from Delta Lake. A date a dated snapshot file serves **is** held and the files are authoritative for it:
an entity that day's file does not list is gone on that date (`DRS-1001` naming the connector), and the store behind is not asked.
`effective` kinds, undated files and the per-entity layout cannot tell what a date holds, so an entity they lack passes to the next
store. A kind with no file or folder at all is not held on any date. There is no time travel: a *known at* read of a date the files may
hold is refused with `DRS-1007` (400), never answered with today's file.

## Loading

```bash
tools/load-files.sh                              # the samples: 1,791 documents x 10 business days, into data/files
tools/load-files.sh --trades 10000               # and a book of 10,000 trades a day for 3 days
tools/load-files.sh /tmp/files --trades 50000    # somewhere else, a larger book
SPRING_PROFILES_ACTIVE=files DRISHTI_PACKS=market-risk,counterparty-risk java -jar drishti-server/target/drishti-server-*-exec.jar
```

`JsonlLoader` (in the plugin; `JsonlLoader FILE|- <root> [--future-days N] [--zone Z]`, run by `tools/load-files.sh [root] [--trades N]
[--days D]`) reads the loaders' rows from a file or standard input and copies each line into `<root>/<domain>/<date>/<kind>.jsonl`:

- **A file the stream reaches is replaced whole**: its lines go to `<kind>.jsonl.tmp`, renamed into place at the end, so a running
  server never reads half a day.
- **Dates are guarded**: a row dated after tomorrow in the business zone (`--future-days`, 1; `--zone`, else `DRISHTI_BUSINESS_ZONE`,
  else `America/New_York`) is not written; the first few are named and the load ends with an error once the other files are in place.
- At most 256 files are open at once (a file closed early is reopened for appending); a row that would land outside the root (a domain
  or kind like `../x`) is refused.

The connector never writes and has no `writes:`; write-back keeps corrections as overlays in the Drishti database and the loader folds
approved ones into the next build ([WRITE_BACK.md](../../docs/guides/WRITE_BACK.md#52-who-performs-the-write)).

## Memory, size and measured results

| Per 10,000 trades a day | Size |
|---|---|
| one day's file | 78 MB (about 7.8 KB a trade, the documents as JSON text) |
| one day's index: ids and offsets | about 1 MB |
| one day's index: 19 promoted fields | about 2.5 MB |

For a million trades a day that is a file of about 7.8 GB and an index of about 75 MB of ids and 230 MB of columns, indexed in roughly
20–30 seconds on 8 threads (an estimate). Files compress about 8:1 with `gzip`, but compressed files cannot be read by offset, so the
connector reads them uncompressed.

Measured with the scale benchmark (`tools/bench/scale.sh`, a 24-thread laptop, `-Xmx2g`, the `files` profile; medians of 25 HTTP
requests; every search exact). The last column is a straight-line **extrapolation**, not a measurement; "flat" means it does not grow
with the book:

| | 10,000 | 25,000 | 50,000 | 1,000,000 (extrapolated) |
|---|---|---|---|---|
| type-ahead (ms) | 8.7 | 8.9 | 7.8 | flat, about 8 ms |
| open a trade (view), first time (ms) | 3.5 | 3.4 | 4.3 | flat, about 4 ms |
| a trade's document, today / a past day (ms) | 2.0 / 1.1 | 2.4 / 0.9 | 1.1 / 2.7 | flat / about 40 ms |
| a range search with `order by` (ms) | 1.1 | 2.1 | 4.0 | about 70 ms |
| a two-field filter (ms) | 1.6 | 3.9 | 7.8 | about 154 ms |
| one portfolio's trades (ms) | 1.8 | 4.3 | 7.7 | about 131 ms |
| impact of a netting set (ms) | 16.8 | 19.0 | 17.1 | flat, about 18 ms |
| a search on another day, first / again (ms) | 192 / 1.1 | 213 / 2.3 | 353 / 4.8 | about 2.9 s (weak fit) / 88 ms |
| load, the whole script (s) | 9.2 | 11.2 | 15.4 | about 164 s |
| store size (MB) | 310 | 688 | 1,322 | about 25 GB |
| server live heap after a full GC (MB) | 89 | 102 | 122 | about 900 MB |

## Limits and trade-offs

- **The first read of a day indexes it**: 0.2–0.35 s for 10,000 to 50,000 lines, tens of seconds for a million. The newest day is
  indexed in the background, older days on first use.
- **One process writes.** Files have no transactions: write a day to a temporary name and rename it.
- **No compression on disk**: a large book takes several times the disk of Delta Lake or PostgreSQL.
- **Only promoted fields are fast** for searches.
- **No time travel** (*known at*): a rewritten file replaces the day.

## The older layout: a file per entity

The connector also reads one file per entity: `<root>/<kind>/<id>.json` (undated) and `<root>/<yyyy-MM-dd>/<kind>/<id>.json`
(dated). The kind is the folder name, the id the file name without `.json`. It suits a handful of documents; for more than a few
thousand entities a day use JSON lines (a file per entity is a file-system entry per entity per day). When a kind has JSON-lines files
they are read first.

```text
/srv/drops/limits/
├── credit-limit/LIM-HARBOURVIEW.json                undated: served when no dated file is found
├── 2026-09-29/credit-limit/LIM-HARBOURVIEW.json     the limit as at 29 September
└── 2026-09-30/credit-limit/LIM-HARBOURVIEW.json     the limit as at 30 September
```

```yaml
# config/connectors/limits-drop.yaml
plugin: file
kinds: [credit-limit]
description: Credit limits dropped by the limits system
settings:
  root: ${LIMITS_DROP_DIR:/srv/drops/limits}
  rescan-seconds: '30'             # new date folders and new ids (for type-ahead) are listed this often
  lookback-days: '5'               # a picked date may fall back at most 5 days to an older date folder
```

No route is needed: the counterparty-risk pack routes `credit-limit` to its lake, which does not hold `LIM-HARBOURVIEW`, so the read
passes on to `limits-drop` (add `routes: { credit-limit: limits-drop }` to ask the folder first). A read for a date takes the newest
dated folder on or before it (within `lookback-days`) that has the file, else the undated one, whose document has no business date (the
view says *No data held for …: the current data of limits-drop, a source that keeps no dates*). Live takes the newest dated folder that
has it. `generation` is the file's modification time. Each read opens the file afresh, so a new file is read at once; type-ahead
catches up at the next rescan. An id with `/` or `..` that would leave the root is refused. The plugin also runs as itself under
`drishti.sources.plugins.file` (source name `feed-file`, root `${DRISHTI_FEEDS:<data dir>/feeds}`).

**CSV** (`<id>.csv`, a header row, read as `{"rows": [...]}` with numbers and booleans typed) is deprecated: each CSV file logs a warning
and health says `UP (CSV input is deprecated: fixing/X.csv (convert to JSON Lines: drishti.py convert))`. `drishti.py convert
fixing/X.csv --rows-document --out fixing.jsonl` writes the JSON Lines line that serves the same document
([CLI_GUIDE.md](../../docs/guides/CLI_GUIDE.md#convert-csv-a-json-array-or-a-folder-of-json-files-into-json-lines)).
