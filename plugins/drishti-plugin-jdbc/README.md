# The jdbc connector

Plugin `jdbc` (`plugins/drishti-plugin-jdbc`): one plugin, two ways to read a database. **Table mode** (setting `table`) reads
the layout `tools/load-postgres.sh` writes, a monthly-partitioned table per data domain, and needs no SQL from you. **Query
mode** (settings `query.<kind>`) reads your own schema as it is, with your own `SELECT` per kind.

## What it reads

- **Table mode:** a data domain (`trading`) is a schema; its kinds share one table `<domain>.entities`, a row per entity per business
  day with the whole document in `doc` and the promoted fields as narrow columns. A sibling table `entity_dates` lists the days, so
  the connector never asks the large table which days exist. Built and measured on PostgreSQL (a million trades a day, seven years).
- **Query mode:** any JDBC database. `query.<kind>` returns one entity; `query.<kind>.<part>` adds parts from other tables;
  `ids.<kind>` (type-ahead), `columns.<kind>` (searches, aggregates) and `reverse.<kind>` (linked entities) each add a capability.
  A kind is dated when its queries use `:asOf`. Without those optional queries a query-mode kind is fetch only.

It is read-only in both modes: its database user needs `SELECT` only. A URL that carries a password is refused.

## Data structure

Table mode, the layout `PostgresLoader` writes (one schema per domain):

```sql
CREATE TABLE trading.entities (
  kind text NOT NULL, id text NOT NULL, business_date date NOT NULL,
  doc  jsonb COMPRESSION lz4 NOT NULL,                       -- the whole document
  "TRADE_ID" text, "PORTFOLIO" text, "QUANTITY" double precision, ...,   -- promoted columns (layout.<kind>.columns)
  PRIMARY KEY (kind, id, business_date)
) PARTITION BY RANGE (business_date);                         -- one partition a month: trading.entities_y2026m09
CREATE INDEX entities_day_ids ON trading.entities (kind, business_date, id);
CREATE TABLE trading.entity_dates (kind text, business_date date, rows bigint, loaded_at timestamptz,
                                   PRIMARY KEY (kind, business_date));
```

- **Id rule:** the `id` column; `(kind, id, business_date)` is the key. Column names can be changed with `kind-column`,
  `id-column`, `date-column` and `doc-column`.
- **Document:** `doc` holds the JSON document as the pack's kind defines it; nested lists stay inside it.
- **Promoted columns:** a path `counterparty.id` is the column `"counterparty__id"` (quoted, case kept); numbers are
  `double precision`, everything else `text`.

Query mode, how a row becomes a document: each column is a field named from its label (`trade_id` becomes `tradeId`, a double
underscore is kept, a quoted label is kept as written); a column named `json` is the whole document; `generation` and
`business_date` columns are read as the version and the date; `json`/`jsonb` columns and those in `json-columns` become nested data.
A part is a list of row objects under the field `<part>` (`part-shape.<kind>.<part>: object` takes the first row). In
`columns.<kind>` the first column is the id. The shipped packs use UPPER_SNAKE names, so with them return the document in one `json`
column (see JDBC_QUERIES.md, section 9).

## Examples

Table mode (the shape of `config/connectors.examples/postgres/`):

```yaml
# config/connectors/trade-endur.yaml
plugin: jdbc
kinds: [trade]
settings:
  domain: trading
  url: ${DRISHTI_PG_URL:jdbc:postgresql://localhost:5432/drishti}
  user: ${DRISHTI_PG_USER:drishti}
  password: ${DRISHTI_PG_PASSWORD}          # or file:/run/secrets/pg-password
  table: trading.entities                   # setting table turns table mode on
  mode.trade: snapshot
  layout.trade.columns: TRADE_ID,SOURCE_SYSTEM,PRODUCT_TYPE,CURRENCY,QUANTITY,COUNTERPARTY,PORTFOLIO
```

Query mode over your own tables:

```yaml
# config/connectors/trading-db.yaml
plugin: jdbc
kinds: [trade, counterparty]
settings:
  url: ${DRISHTI_TRADES_URL:jdbc:postgresql://db:5432/trades}
  user: ${DRISHTI_TRADES_USER:drishti}
  password: ${DRISHTI_TRADES_PASSWORD}
  query.trade: SELECT * FROM trades WHERE trade_id = :id AND business_date = :asOf
  query.trade.legs: SELECT leg_no, pay_receive, fixed_rate FROM trade_legs WHERE trade_id = :id ORDER BY leg_no
  ids.trade: SELECT trade_id FROM trades WHERE business_date = :asOf
  columns.trade: SELECT trade_id, mtm, notional, book, netting_set FROM trades WHERE business_date = :asOf
  reverse.trade: SELECT trade_id FROM trades WHERE netting_set = :target AND business_date = :asOf
  query.counterparty: SELECT * FROM counterparties WHERE id = :id
```

Load table mode with `tools/load-postgres.sh jdbc:postgresql://localhost:5432/drishti` (add `--trades N --days D` for a
generated book, `--keep-months N` for retention).

## Troubleshooting

- `DOWN: <driver message> (reconnecting)`: the database is unreachable or the credentials are wrong; check `url`, `user`,
  `password`. Connections reopen by themselves.
- `UP (not laid out as the pack declares: trade (0 of 19 columns); searches read documents)`: the table lacks the promoted
  columns; reload with `tools/load-postgres.sh`.
- `not a plain SQL identifier: ...`: `table` or a column name holds more than letters, digits, `_` and one `.`.
- A view fails with `… its query query.<kind>.<part> failed (SQL state …)`, Health `DEGRADED: query.<kind>.<part> failed: …`:
  run that query in a client with the parameters filled in.
- Searches say `partial: true`: the field is not promoted (table mode) or not a column of `columns.<kind>` (query mode).
- `tls.* is set and the url also carries driver TLS options (sslmode, sslrootcert, ...): give TLS one way`: use one form.

Every health text is in the full documents, sections *Diagnosing*.
