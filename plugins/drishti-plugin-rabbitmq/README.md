# The rabbitmq connector

Plugin `rabbitmq` (`plugins/drishti-plugin-rabbitmq`, on the shared `MessageStateSource` of `drishti-messaging`, as `activemq`):
entity changes from RabbitMQ queues, kept on local disk, with views that update on every message.

## What it reads

One AMQP connection and one channel, named `drishti-<source-name>`. For each queue in `queues` it declares the queue durable (unless
`declare: false`), binds it per `bind.<queue>` (`exchange:routing.key`; the exchange must exist), and consumes with manual
acknowledgement and `prefetch` (100). Each delivery is written to the **state store** (RocksDB under `<state.root>/<connector name>`),
the memory cache and type-ahead, pushed to open views, and then acknowledged; one the store could not keep is returned
(`basicNack`, requeue) and delivered again. All queues of a connector share the channel, so deliveries are applied one at a time.
Undated, no reverse lookups. Consumers of one queue share its messages: give each Drishti server its own queue.

## Data structure

The body is JSON in UTF-8. Read from the message: header `id` (the entity id), property `message_id` (the id when there is no `id`
header) and header `deleted` (`true` deletes). Routing key, exchange, content type and other headers are ignored.

- **A queue with a kind** (`kind.<queue>`, or `kind`): the body is the document, stored as it is. **Id rule:** the `id` header, else
  `message_id`, else the body's field `id-field.<queue>` (else `id-field`, default `id`).

  ```text
  queue: drishti.margin-calls     (kind.drishti.margin-calls: margin-call, id-field.drishti.margin-calls: CALL_ID)
  headers {"id": "MC-CORAL-FRA-2"}   (optional)
  body: {"CALL_ID": "MC-CORAL-FRA-2", "MARGIN_TYPE": "Variation", "AMOUNT": 128000.0, "STATUS": "Settled",
         "EVENTS": [{"AT": "2026-09-28 09:05", "EVENT": "Call issued", "BY": "collateral-system"}, …], "CURRENCY": "USD"}
  ```

- **A queue without a kind:** an envelope `{"kind": "netting-set", "id": "NS-CORAL-FRA", "doc": {…}}`; the envelope's `id` wins over
  the header. One queue can carry any number of kinds.
- **Deletes:** header `deleted: true`; an envelope with `"doc": null` or no `doc`; an empty body with an `id` header on a queue with a
  kind. Pushed to open views (greyed, with when it was deleted).
- **Rejected** (counted, acknowledged, dropped): not JSON, no kind, no id, or an empty body on a queue without a kind.
- **Stored:** the document under `<kind>/<id>`; provenance `live: true`, no business date.

## Examples

```yaml
# config/connectors/margin-mq.yaml
plugin: rabbitmq
enabled: ${DRISHTI_MARGIN_MQ:false}
kinds: [margin-call]
settings:
  uri: ${RABBIT_URI}                      # amqps:// for TLS
  queues: [drishti.margin-calls]
  bind.drishti.margin-calls: collateral:margin.#
  kind.drishti.margin-calls: margin-call
  id-field.drishti.margin-calls: CALL_ID
  state.max-gb: '20'
  stale-after: 30m
```

Ready-made files in `config/connectors.examples/other/`: `orders-queue.yaml` (`amqps://`, PKCS12 truststore) and
`rabbitmq-external.yaml` (the certificate is the log-in). There is no loader: producers publish messages.

## Troubleshooting

- `DOWN: ConnectException: Connection refused (retrying)`: the broker is not listening there; fix `uri`.
- `DOWN: AuthenticationFailureException: ACCESS_REFUSED … (retrying)`: wrong user or password (URL-encoded in the URI).
- `DOWN: IOException: … (retrying)` with `PRECONDITION_FAILED - inequivalent arg` in the broker log: the queue exists with other
  arguments (quorum, TTL, DLX); set `declare: false`.
- `DOWN: connection lost (recovering)`: automatic recovery is reconnecting every `recovery-interval-ms`.
- `DOWN: consumer cancelled on <queue>`: the queue was deleted; recreate it and restart the server.
- `UP` but nothing arrives: the queue is not bound to the producer's exchange, or another consumer takes the messages.

Every health text is in the full document, sections *Failure and recovery* and *Diagnosing*.
