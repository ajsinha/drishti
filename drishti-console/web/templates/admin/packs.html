Packs

{% with tab='packs' %}{% include "admin/_nav.html" %}{% endwith %}

A pack brings a domain: its kinds, mnemonics, layouts and connectors. Switch a loaded pack off and, at everyone's next click, its kinds cannot be opened, its mnemonics and suggestions disappear, and it leaves every pack menu. Switch it on and it all returns. A pack another pack builds on stays on until that one is off; switching a pack on switches on what it builds on. The choice is kept across restarts and recorded in the audit log. Load brings in a pack that is on disk but not loaded: it is checked with the loaded packs first, then it is in use at once, with no restart. Unload takes back a pack loaded here (not while another loaded pack builds on it). The server also watches the packs folder: a pack folder you add is loaded, one you edit is checked and swapped in (a bad edit keeps the last good version and shows its problem here and on Health), and one you delete is unloaded. Sample packs are demonstrations; once real packs exist, hide them from business users (below). Deploy an archive (below) brings a new version of a pack from a file: it is checked, you see what it changes, and only then is it deployed; the version it replaces is kept so you can Roll back. Data source shows the connectors a loaded pack reads through, with links to Admin → Connectors, where they are created, tested and changed.

Deploy an archive

Choose a pack archive: a .tar.gz made by drishti.py pack bundle or pack make (or a .zip). The archive carries the pack only, never data. The server checks it before anything changes: its checksums and manifest, that no path leaves the pack folder, the server version it needs, the Sutras (lint and tests), the packs it builds on, and an optional signature. Then you see what it would change from the running version, with breaking changes marked, and confirm.

Signed archive?

The publisher's key must be listed in drishti.packs.registry.trusted-keys. Unsigned archives are accepted unless the server requires signatures.

History and roll back

Every deployment and rollback, newest first. The last few versions of a pack are kept so it can go back; rolling back is itself kept, so it can be undone. If the server cannot start with new files it puts the old ones back by itself and the history says reverted.
